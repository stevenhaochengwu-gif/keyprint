# Keyprint

Keyprint is a browser typing trainer that lives in one file, `index.html`, with no build step, no dependencies and no tests. It has five kinds of test. Step up (the default, where each day starts short, every perfect test adds a word and three mistakes take one away), Words, Adaptive (letters unlock one at a time as you learn them), My text (your own pasted text, text files or PDFs) and Write (you type a few questions about a piece you're about to write, to think it through, and then write it on the same screen). Tests can also be in Chinese, everyday words typed with a pinyin input method, with the pinyin above each character. Two rows above the text show how well you type each key, the letters and under them the punctuation marks and digits your tests hold. In English Step up and Words, your weakest keys from recent tests are outlined there and come up more often, with about a third of each test's words picked to hold a weak letter. It also has an on-screen keyboard with finger colors and hand outlines, daily goals (reaching the clean typing one sets off the page's biggest celebration), a Progress page of canvas charts, and an Analysis page that works out where your mistakes come from (keys, confusions, key switches, Shift, fingers, pace, place in the word) and builds a Practice these test from them. Someone new gets a four step welcome over their first test, which Settings can show again. Progress saves in the browser, or in Claude artifact storage when it runs as an artifact. On the site, an account (an email address and password with a code to confirm the address, or Sign in with Google) keeps it on every device through a small account service in the site's own Worker, `site-worker.js`. An account can carry your name, which shows as initials on a key cap at the end of the top bar, or a picture in their place, and progress already in a browser joins the account you sign in to with no question. Until the site has a mail service set up, accounts take a username instead, as they did at first, and those usernames keep signing in afterwards. Key based Cloud save, to a Cloudflare Worker that the user runs, still works as before.

## Files

- `index.html` is the entire app, about 15,600 lines of HTML, CSS and JS. Keep it one self-contained file. The owner also runs it as an artifact in the Claude chat app (that is where `window.storage` comes from), so don't split it into modules or add local files, packages or a build step.
- `README.md` is a one-line stub.
- `wrangler.jsonc`, `.assetsignore` and `_headers` deploy the site to Cloudflare (see Deploying). `_headers` is page header config (no framing, `nosniff` and a referrer policy) that Wrangler reads and never publishes.
- `site-worker.js` is the site Worker's script and the account service behind `/api`. It also sends the account emails (through Resend) and asks a model for the questions and the word lists behind Write, Cloudflare's Workers AI through the `AI` binding, or Claude on a site with a key. Those are the only places it reaches outside itself. It's an ES module exporting `default { fetch }` and two Durable Object classes on SQLite, `Directory` and `Vault`. It has no imports, no packages and no `nodejs_compat`, uses only Web APIs and the Durable Object SQL API, and reaches both classes through plain `fetch` handlers and `stub.fetch` rather than RPC, so Node can import a copy for tests. Unlike `save-worker.js`, it deploys automatically with every push to `main`, and `.assetsignore`'s `*.js` keeps it off the site. Its header points here for the routes and every answer they give, so keep the account service notes below in step with it.
- `save-worker.js` is the Cloudflare Worker behind key based Cloud save (an ES module, `export default { fetch }`). It stores everything in a Workers KV namespace bound as `DATA` and only answers requests with `Authorization: Bearer <SAVE_KEY>`. The owner deploys it by hand in the Cloudflare dashboard, so editing this file changes nothing live. Say so whenever a change needs a redeploy, and keep the app working with the Worker that is already deployed. Accounts don't use it, and key based Cloud save must keep working with it unchanged.

## Deploying

The site is a Cloudflare Worker that serves `index.html` as a static asset and runs `site-worker.js` (`main`) for the account service. `wrangler.jsonc` names that Worker (`typing`, which must match the dashboard exactly), keeps its workers.dev address and declares the `type.stevenwu.org` custom domain. Once the owner connects the Worker to this repo under Settings, Build, every push to the production branch (`main`) runs `npx wrangler deploy`, which publishes the page and the script together.

- **`run_worker_first` is `["/api/*"]`.** Never make it `true`. Every page load would then run the script, count against the Free plan's 100,000 Worker requests a day and get a 429 instead of the page once they run out. Page loads match `index.html`, so they stay free static files. Paths with no file still run the script, which answers them with the usual 404 through `ASSETS`, so crawlers and scanners asking for missing paths count as Worker requests. If that noise ever matters, a WAF rule or rate limit on the zone is the lever. The array form needs Wrangler 4.20 or later, and the build's `npx wrangler deploy` isn't pinned, so it gets the latest.
- **Durable Objects.** The bindings `DIRECTORY` and `VAULT` point at the classes `Directory` and `Vault`, which the migration tagged `accounts-1` (`new_sqlite_classes`) creates on the first deploy from `main`. Never rename the Worker, a class, a binding or the tag, and never remove the migration entry, or deploys fail or the site points at empty storage. A new class needs a new migration entry with a new tag. A new table needs none, since the classes create their own with `CREATE TABLE IF NOT EXISTS`, but the Directory does that in its constructor and a Vault only in `session-new`, so an existing account gets a new Vault table only at its next sign in, and code has to cope until then. A new column in an existing table needs an `ALTER TABLE`, because objects that already exist keep their tables.
- **Preview builds** can't apply a Durable Object migration, so builds of other branches fail until the first deploy from `main`. Keep builds for non production branches off.
- **Workers AI.** The `ai` block in `wrangler.jsonc` binds Workers AI as `AI`, which writes Write's questions and makes its word lists with no key and no secret. The Free plan includes 10,000 Neurons a day across the whole Cloudflare account, and `WRITE_AI` costs 5,500 of them for a million tokens read and 36,400 for a million written. A first answer holds a piece's questions and its word list, so it costs about 17 for a short prompt (about 35 in Chinese, whose questions and entries carry pinyin), about 50 with a full English document and at most about 240 with the longest document in any language (`WRITE_BYTES` read at up to a token a byte, plus `WRITE_AI_TOKENS` written). That's a few hundred pieces a day from prompts and at least 40 from the longest documents, and one account's `WRITE_PER_DAY` can take about half a day's allowance at worst. A list for a piece that's under way (see Write under The account service) reads at most `WRITE_SOFAR_BYTES` and writes at most `WRITE_MORE_TOKENS`, so it costs about 10 and at most about 65 (the task, a prompt that can be 1,800 bytes in Chinese and the piece's 3,600 read, 800 tokens written), and one account's `WRITE_MORE_DAY` (100) comes to about a tenth of a day's allowance as a rule and two thirds of it at worst. Past the allowance the Free plan charges nothing. The call throws, the route answers 503 `later`, and until 00:00 UTC a new piece's warm-up asks the general questions and its words come from your own, while the strip under a piece that's under way moves on through the list it has. Models that need a paid plan (Cloudflare's pricing page lists them) would fail the same way, so check that page before changing `WRITE_AI`. The Worker's log tells these apart by the Workers AI error code (see Write under The account service).
- **Vars.** `GOOGLE_CLIENT_ID`, `GOOGLE_ORIGINS` and `MAIL_FROM` live in `vars` in `wrangler.jsonc`. The client ID isn't a secret, and leaving it empty (as it is now) turns Sign in with Google off. `GOOGLE_ORIGINS` lists the origins registered with that Google client, comma separated, and only those pages show the Google button. `MAIL_FROM` is the sender of the account emails, like `Keyprint <hello@example.com>`, on a domain verified with Resend. It's `Keyprint <hello@email.stevenwu.org>` now, on `email.stevenwu.org`, which the owner verified there. Every deploy overwrites vars set in the dashboard, so change them in the file.
- **Secrets.** None are required, and all are set only in the dashboard, where deploys never remove them. `RESEND_API_KEY` is a Resend API key. Email accounts switch on when it and `MAIL_FROM` are both set (`mailOn`), and until then the site takes usernames. `ANTHROPIC_API_KEY` is a Claude API key, which costs money and is off. With it Claude writes Write's questions and makes its word lists in place of Workers AI, and without it Workers AI does. The optional `PEPPER` must never change or go away once it's set (see Gotchas).
- **Turning email accounts on** takes three steps, in this order. Verify a sending domain at resend.com (it gives DNS records to add in Cloudflare) and make an API key. Add the key as the secret `RESEND_API_KEY` on the `typing` Worker. Put the sender in `MAIL_FROM` in `wrangler.jsonc` and merge to `main`. Resend's free plan sends 100 emails a day, which is why `MAILS_PER_DAY` is 90, so raise that constant with a bigger plan.
- Beyond `ASSETS`, the two Durable Objects and `AI` there are no bindings. There's no `ratelimits` binding (its status on the Free plan isn't documented), no `secrets.required` (it would fail the first build), no `previews` block and no observability logs (logs could capture headers). Keep it that way.

The assets directory is the repo root, so `.assetsignore` must keep everything except `index.html` off the site, above all `.git`, which can hold a GitHub token on the build machine. When you add a file to the repo, check whether it would be published (`git -c core.excludesFile=.assetsignore check-ignore --no-index -v <path>` shows the matching rule) and extend `.assetsignore` if it shouldn't be. `site-worker.js` matches `*.js`. `_headers` shows as not ignored, which is expected, because Wrangler always takes `/_headers` as config and never uploads it. Its headers only reach static responses (`/api` sets its own), and they don't affect the Claude artifact. Never add Cross-Origin-Opener-Policy there, which would break the Google popup. `save-worker.js` is deployed separately by hand and isn't part of this.

## Running and checking changes

Open `index.html` in a browser, or serve the folder with `python3 -m http.server 8000` and visit http://localhost:8000/. Accounts don't work in either. On `file://` the Account group in Settings says `Accounts work at type.stevenwu.org. Here, your progress stays in this browser.`, and under `python3 -m http.server` the config check gets a 404, so it says `Accounts aren't available at this address. They work at type.stevenwu.org.` The welcome's last step suggests a backup file in both (see The welcome). The rest of the app works as before. The only network requests are Google Fonts, pdf.js 3.11.174 from cdnjs (loaded only when a PDF is added, with SRI once `APP.pdfIntegrity` is filled in), `/api` on the page's own origin (the config check when Settings opens, or before Write first asks this site for a list, then sign in calls, an account's saves, a read of the account when someone signed in comes back to the page, its picture when that changed and, for someone signed in, one `/api/write/field` request for each piece started in Write and one more each time the words under a piece change, unless Words follow your piece is off), Google's script `APP.googleScript` (only while Settings shows a Google button on an origin in `GOOGLE_ORIGINS`) and the user's Cloud save address.

In this cloud environment Chromium and Playwright are preinstalled, `require('playwright')` works, and `chromium.launch()` needs no options. A `file://` URL is fine and gets working localStorage. Google Fonts fail here with `ERR_TUNNEL_CONNECTION_FAILED`, which is expected. Listen for `pageerror`, because one syntax error anywhere stops the whole app. `celebrate(["clean"], false)` from `page.evaluate` sets off the boom and `celebrate(["total"], false)` the release, and `playBoom(title, detail, seed)` plays a boom that's the same every time. Playwright's clock (`page.clock.install()` before `goto`, then `runFor`) moves the boom's own drawing but not its CSS animations. Top-level `const` and `let` names (`state`, `lesson`, `APP`, `Store`) can be read from `page.evaluate`. After load, keystrokes go to the hidden `#sink` input, which has focus unless the welcome is open (then the dialog has it). Each `browser.newPage()` starts with empty storage, so it is someone new, and the welcome opens over the first test. It's a modal dialog, so until it closes it takes every key and makes the rest of the page inert, and a `page.click` on a tab or button times out. A script that isn't about the welcome sets `window.keyprintNoWelcome = true` with `page.addInitScript` (or `context.addInitScript`, which also covers new pages) before `goto`. It lasts through reloads, which a sign in, a sign out and `leaveTab` all cause, and then the welcome only opens from Settings (or `openWelcome(false)`). To test an old or odd save, seed `keyprint-state-v1` with `page.addInitScript` before `goto`. Keep test scripts and screenshots outside the repo.

To test Cloud save end to end, run the real Worker locally. Copy `save-worker.js` to a temporary `.mjs` file with the test app's origin added to `SITES`, import it in Node 22, and serve it with `http.createServer` by turning each request into a `Request` and calling `worker.fetch(request, { DATA, SAVE_KEY })`. A `Map` behind async `get`, `put`, `delete` and `list({ prefix, cursor })` (returning `{ keys: [{ name }], list_complete, cursor }`) stands in for KV. Serve `index.html` over http from that origin, not `file://`, or CORS blocks everything. Use one browser context per simulated device, each with the `keyprintNoWelcome` init script unless the test is about the welcome, and set `timezoneId` on a context to test time zone behavior. The stand-in KV is instantly consistent and has no rate limit, so wrap it when a test needs real KV behavior.

```js
const { chromium } = require('playwright');
(async () => {
  const browser = await chromium.launch();
  const page = await browser.newPage();
  page.on('pageerror', (e) => console.log('pageerror', e.message));
  await page.addInitScript(() => { window.keyprintNoWelcome = true; }); // skip the welcome
  await page.goto('file:///home/user/keyprint/index.html');
  await page.waitForFunction(() => document.querySelector('#text .c'));
  const text = await page.evaluate(() => lesson.text);
  await page.keyboard.type(text.slice(0, 10));
  console.log(await page.evaluate(() => lesson.pos)); // 10
  await page.screenshot({ path: '/tmp/keyprint.png' });
  await browser.close();
})();
```

To test accounts end to end, build a harness in a scratch folder outside the repo (none is checked in) around the real `site-worker.js`, in Node 22.

- Each fresh context is someone new, so give it the `keyprintNoWelcome` init script with `context.addInitScript` unless the test is about the welcome. Signing in, signing out and other tabs reload pages, and the script covers every reload.
- Copy `site-worker.js` to a `.mjs` file and import it. It needs no stubs. To try a different limit (a lower `SIGNUPS_PER_DAY`, say), swap the text in the copy.
- Fake the two Durable Object classes on `node:sqlite`, and run Node with `--no-warnings` to hide its ExperimentalWarning. Each instance's `ctx.storage.sql` wraps a `DatabaseSync(":memory:")` whose `exec(query, ...bindings)` takes ArrayBuffer bindings, gives BLOBs back as ArrayBuffer, refuses BEGIN and COMMIT as workerd does, and returns a cursor with `toArray()`, `one()` and iteration. `ctx.storage` also needs `transactionSync(fn)` (BEGIN, then COMMIT, or ROLLBACK on a throw), `deleteAll()` and `setAlarm()`, plus a way to fire `alarm()`. A namespace has `idFromName(name)` and `get(id)`, whose stub's `fetch(input, init)` calls the one instance for that name with a new `Request`. Don't serialize those calls, because real objects interleave at every await that isn't storage, and the burst tests depend on that.
- Serve it with `http.createServer` on `http://localhost:<port>`, a secure context where accounts work, by calling `worker.default.fetch(request, env, { waitUntil() {} })` with `env = { ASSETS, DIRECTORY, VAULT, GOOGLE_CLIENT_ID, GOOGLE_ORIGINS }`. Adding `RESEND_API_KEY` and `MAIL_FROM` to it switches email accounts on, and an `AI` object with `run(model, input)` or `ANTHROPIC_API_KEY` the word list route. Without them every test runs in username mode, as before.
- Fake the two outside services the same way as Google. Wrap `globalThis.fetch` so `https://api.resend.com/emails` keeps each email it's sent (the tests read the six digit code from its text) and `https://api.anthropic.com/v1/messages` answers with a message whose content starts with a `thinking` block and then a `text` block of lines, or with a refusal, an error status or no answer at all. Workers AI isn't a fetch, so its stand-in is the `AI` object itself, whose `run` keeps each call and answers like a chat completion (`choices[0].message.content`), in the older `{response}` shape, with a think block first, with a refusal, by throwing as a used up allowance does, or never. Swap `AbortSignal.timeout(25000)` for a short one in the copy to test a model that hangs. In a browser test of Write, a page that isn't loading a test only shows the box or your piece, so wait for `lesson || drafting() || !el.writeSetup.hidden` instead of `#text .c`. `ASSETS.fetch` answers `/` with `index.html` read from disk and anything else with 404. Set `CF-Connecting-IP` from a test header, so each simulated device has its own address and the per address limits don't pile up. A second server without the bindings shows the not set up path, one whose `GOOGLE_ORIGINS` leaves the page out shows the Google hint, and `http://127.0.0.1:<port>` stands in for workers.dev.
- Fake Google on both sides. A new Google account takes two POSTs to `/api/auth/google`, the question (`create` false) and then Create it (`create` true), and `api.clock.offset` in the dev kit's harness moves the site's clock past a credential's hour. In Node, make RS256 key pairs with WebCrypto, wrap `globalThis.fetch` so `https://www.googleapis.com/oauth2/v3/certs` answers with the public keys (with a `max-age`), and sign ID tokens with any claims. In the browser, `context.route(APP.googleScript, ...)` serves a stand-in for Google's script whose `google.accounts.id.initialize` keeps the config, nonce included, and whose `renderButton` draws a plain button that hands the callback `{ credential }`. `page.exposeFunction` lets the page ask Node to sign a token for the current nonce.
- Patch `Date.now` in Node for the server's clock (sessions, limits, daily copies, a new account's smaller budget) and use `page.clock` for the app's timers. Setting `APP.accountDelay` lower through `page.evaluate` makes saves come sooner.
- A browser with progress joins the account it signs in to with no question, so a test waits for the toast, not the merge row. The note about what came along (`Account.message.once`) then stands in for the usual Signed in as note until the test leaves Settings, and a named account's toast is `Welcome, <first name>` or `Welcome back, <first name>`. The first Create account click also shows the name field, which a test can leave empty.
- Coming back to the page reads the account (`pullCloud`). A test brings that on by setting `Account.pulledAt` to 0 and dispatching `focus` or `online` on the window, or `visibilitychange` on the document. Any key or click does it too, so a test that counts requests should expect one read of `keyprint-sync` at the first key or click once two minutes have passed since the account was last read, which `page.clock.fastForward` brings about.
- To test moving key Cloud save progress into an account, run the real save Worker beside it as above, with the account server's origin in `SITES`.

While you write a piece in Write there's no lesson, the draft textarea `#draft` has the keys, and `onKeyDown` hands anything typed elsewhere on the page to `draftKey`. Each settings control is bound by `data-setting="<key>"` through `bindSettings`. It then goes through `setSetting`, which runs the refreshers listed in `EFFECTS` and saves. The Account group isn't settings and has no `data-setting`. `bindAccount` (called from `bindEvents`) binds its buttons, `showView("settings")` calls `openAccount`, and `renderCloudStatus` ends with `renderAccount`, so the 30 s Settings refresh reaches both. `renderAccount` ends with `renderWho`, which draws the account's key cap in the top bar whatever view is showing, so every cloud save brings it up to date as well.

The script changes the look mostly through root attributes (`data-theme`, `data-font`, `data-zoom`) and classes, plus a few inline styles for timing and position (`--fade` on the board, `--leave` on the cheer, caret and text transforms). In the other direction, canvases and confetti read colors from CSS variables through `palette()` and `burst()`.

## State, storage and versioning

- **The `state` object.** It holds `version, settings, profiles, daily, clean, goalMetOn, cheered, docs, docId, removed, step, restoredAt, drillBack, devices, welcomed, writes, writeId, savedAt`. `writes` are the pieces started in Write and `writeId` the one it's on (see Saved shapes and Write in Gotchas). `drillBack` is `"zh"` while Practice these has switched Chinese off and `""` otherwise (see Practice these in Gotchas). `welcomed` is when the welcome was closed (ms), or 0 for never. `step` is `{day, words, at}`, how long Step up's tests are on that local day and when that was last set (ms, set by `finishLesson` after every perfect Step up test, at Top too, and every step down, 0 in saves from before it was timed). English and Chinese Step up and every layout share it. `finishLesson` sets `at` to now or one past the `at` it replaces, whichever is later, so a change always beats the copy it changed even when another device's clock is ahead. `hydrate` clamps `at` to between 0 and a day past now. Don't hold it closer to now, or a fast clock's `at` is lowered here but not in that clock's own copy, which then undoes the next change made here. `mergeSaves` keeps the later day's, or on the same day the later change (see `mergeSaves`). Each `profiles[layout]` is `{unlocked, keys, history, customPos, resetAt}`, so letter stats, unlocks and history are kept per layout. `daily` and `clean` (ms per local `YYYY-MM-DD`) are shared by all layouts.
- **Saved shapes are fixed.**
  - Letter stats are `{t, n, e, m, x}`.
  - History entries are `{ts, wpm, acc, dur, words, mode, tries, nk, k, tx, mx, tm}`, with `k[ch] = [avgMs, timed, typed, missed]`. Older entries have no `k` or `nk` and must keep working. A Chinese test has `lang: "zh"` and no `nk`, `k`, `tx`, `mx` or `tm`. Entries without `lang` are English. An entry can also have `at`, when it joined this record (ms), set only on a guest's tests from before the account's last Reset progress when they join it on sign in (see `adoptAccount`). `mergeSaves` counts such a test from `at` where it would count it from `ts`, keeps the larger `at` of the two copies, and everything else reads `ts` as before.
  - `tx`, `mx` and `tm` are every keystroke of the test, for the Analysis tab, made by `keyDetail` and `joinDetail` in `finishLesson`. `tx` is the test text. `mx` is `[[i, typed, ms], ...]`, the first wrong key at each position `i` of `tx` that went wrong, with the ms since the key before (left out when there is none, at a test's first key or right after Backspace). Wrong keys typed after it while the mistake still shows (the trail, and every blocked key with Backspace to delete) are not noted again, so `mx` lines up with `errAt`. `tm` is two base 36 digits per character of `tx` (so `tm.length === 2 * tx.length`), the time before the key that typed it right on the first try in 10 ms steps, capped at `APP.idleGap`, or `zz` when there is none (first key, after Backspace, or a missed position).
  - Attempts that end early (a failed try in One mistake restarts, Esc, Tab, a settings change) have no entry of their own. `keepPartial` holds their keys in `unfinished` (not saved, at most `APP.unfinishedChars` characters, dropped on a layout change or Reset progress), and the next finished test on the same layout puts them first in its `tx`, each part ending in a `\n` with `zz` in `tm`. Lesson text never contains `\n`, and the analysis never counts a switch across one. So `tx` can be longer than the text the entry's `wpm` and `acc` describe.
  - Only the newest `APP.detailTests` tests per layout, holding at most `APP.detailChars` characters of `tx`, keep these three fields. `trimDetail` strips the rest, and both `finishLesson` and `hydrate` run it, so merges can't grow it back. Old entries without them, or with ones that don't add up, are skipped by `detailedTests` and work everywhere else as before.
  - Pieces from Write are `{id, title, prompt, list, asks, zh, made, text, v, edited, added, typed, ms}`, cleaned by `cleanWrite`. `list` is the word list (for Chinese, each entry is the word and then its pinyin, as in `ZH_WORDS`), `asks` the questions its warm-up asks (at most `APP.writeAsks`, each a string that `askOk` passes, and for Chinese the question's words with a space between them, a bar and the pinyin of every character, as `cleanAsk` leaves it), `made` whether the list was made for the piece rather than taken from your own words, `text` what you wrote, `typed` and `ms` the characters typed into it and the typing time (still kept, though nothing shows a writing speed any more), and `v` the number of edits each browser made, by device id. `list` changes as the piece grows, when the words under it change (see Write in Gotchas). A piece with fewer than `APP.writeAskMin` questions of its own (one from before pieces had them, or one no model could be asked about) asks the general ones. Unlike a text in My text, a piece's words are in the main blob, on purpose, so every save, left copy, daily copy and backup has them and a merge can keep both sides. A removed piece's id goes in `removed`, which pieces share with texts, and its words can live on in daily copies (14 days in an account, for good in a save Worker). Ids follow the doc id rule.
  - Docs are `{id, title, words, passages, at, added, finished}`. Doc text is never stored in the main blob, which is why My text tests keep no `tx`, `mx` or `tm` (`finishLesson` and `holdPartial` skip them). Otherwise a removed text's words would live on in the main save and in the cloud's daily copies, which the save Worker never deletes (an account keeps the last 14).
- **`Store`.** It uses Claude's `window.storage` if present, then localStorage, then nothing. It writes four kinds of key (plus a `keyprint-probe` it sets and removes to test localStorage).
  - `keyprint-state-v1`, the whole state.
  - `keyprint-doc:<id>`, one per text.
  - `keyprint-cloud`, this browser's cloud config (the shapes are below), always with this browser's `device` id (8 to 24 lowercase letters and digits).
  - `keyprint-face`, `{user, data}`, this browser's copy of the picture of the account it's signed in to (`user` is the account's id and `data` a small JPEG as a data URL), so the key cap shows it before the account has been read. `keepFace` writes it and `loadFace` reads it, and a copy kept for another account never shows.

  Never rename these keys, or every existing save is orphaned. `wipeLocal` removes the first two kinds and the picture straight from localStorage, which is the only place accounts exist.
- **The `keyprint-cloud` shapes.** `loadCloudConfig` reads them and `saveCloudConfig` writes them. `cloudSeen` holds the raw text this tab last read or wrote.
  - `{url, key, device}` is the older key config, still read as key mode, and `{kind: "key", url, key, device}` is what key mode writes now.
  - `{kind: "account", url: "", key, device, user, due, held, heldAt}` is an account. `url` stays empty so an `index.html` cached from before accounts sees Cloud save as off and never sends the token anywhere. `key` is the session token, or empty once the session has ended, when this browser's progress still belongs to `user` (`{id, name, username, email, login, google, password, called}`, cleaned by `cleanUser`, which fills `login` from `username` for a config saved before `login` existed and gives `called`, the name the account shows, as `""` for one saved before names). `due` lists texts not yet in the account and `held` texts it had no room for (at most 300 ids each, checked by `textIds`), and `heldAt` is when one was last held.
  - `{device, out, why, fresh}` is the signed out marker, and Cloud stays off while it's there. `why` is `out`, `deleted`, `revoked` or `cleared`, and `fresh` stays true until the first load after the sign out has wiped whatever a stale tab wrote.
  - An account config is taken only where `accountPlace()` is `"ok"`, and its token only when `isToken` finds it well formed and naming `user.id`. The token never goes into the DOM, a URL, a backup file or the state blob.
- **Saving.**
  - `scheduleSave` debounces (400 ms by default, 500 from `setSetting`), then calls `saveLocal`.
  - `saveLocal` stamps `savedAt`, writes, marks the cloud copy dirty and calls `scheduleCloud`, which pushes at most every `APP.cloudDelay` (20 s), or every `APP.accountDelay` (a minute) for an account. Before any of that it returns at once while `ready` is false, and calls `leaveTab` instead of writing when another tab has signed in or out since this one last looked (see Tabs, signing in and signing out).
  - `flushSaves` runs on `pagehide` and when the page is hidden. It saves locally, then `sendLeaving` sends a slim copy with `keepalive` to this browser's own slot, `keyprint-pending-<device>`, once per batch of changes. The copy carries `leftAt` (this browser's clock) and only this browser's own `left` mark, since its other marks may cover copies whose tests it isn't carrying. The copy holds only tests since this browser's last cloud save (at most `APP.pendingTests` per layout) and the last 3 days of totals, since merging only ever adds. Only the newest of those tests keep `tx`, `mx` and `tm`, up to `APP.leftDetail` characters of them, and the rest reach the cloud with the next regular save. Of the pieces from Write it carries only the ones edited since then, whole. A long one can take the copy past the size `keepalive` allows, and then it rides on the next regular save. It never writes the main cloud copy, because a hidden page may never run again (phones often stop one right away) and a closing page can't wait to read first. Nothing is sent while `Account.switching`.
  - `pushCloud` runs one `sendCloud` at a time and queues at most one more for everyone who asks meanwhile. Keep it that way, or two saves read the same copy and both write it.
  - `pullCloud` is how an account catches up without a reload, and how a save that failed offline goes through once you're back. It runs when the page shows again, the window gets focus or a page comes back from the back forward cache (`back`), when the browser goes back online (`online`), and on any key or tap (`touch`), which covers a page left open and in front that gets none of the others (all bound in `bindEvents`). It does nothing in key mode, signed out, while a save is running, or while a save that didn't fit (`full`) waits for its own timer. It asks for a cloud save at most every `APP.accountPull` (2 minutes) since the account was last read (`Account.pulledAt`, which every `readAccount` sets), or every `APP.accountAgain` (15 s) while `Cloud.error` is `reach`. Back online also starts the retry waits over. A key or a tap never asks while there's an error, or typing through an outage would ask every few seconds where the waits are meant to grow. So while you practice, when a save reads the account every minute anyway, it never fires, and the first key after a break does. `pulledAt` is wall clock time, not `performance.now()`, because a sleeping computer's page clock stands still and the morning after is when there's most to catch up on. With changes waiting (`cloudDirty`) that's an ordinary save. With none it sets `cloudPull`, and `sendCloud` then only reads. It merges what it read into this browser, saves that locally with `Store.save` behind the identity check (not `saveLocal`, so nothing is marked dirty), keeps the copy's mark (`Cloud.mark`), starts `uploadDue` and `retryHeld` as a save that works does, and writes nothing to the account. Left copies it folded in stay in the account, and its `left` marks are only in this browser, so the next save from any browser still folds them into the main copy. A read that fails is noted like a failed save, and its retry is a read again, though only while the page can be seen. A hidden page waits, and coming back to it reads (`pulledAt` only moves on a read that worked). Being back online reads too, except in a hidden tab with nothing waiting to go up. Those reads are why syncing needs no polling. Nothing asks the account on a timer while you only look at the page.
  - `sendCloud` first waits until 1.1 s after its last successful PUT (timed with `performance.now()`, as KV takes one write a second per name). Then `readCloud` reads the main copy and the slot of every browser listed in `state.devices` and in the main copy (an account reads them all in one request instead), `foldLeft` merges each slot whose `leftAt` is newer than that browser's `left` mark and raises the mark, and the main copy is written. Slots are never deleted. The marks make sure each left copy is merged once. It gives up quietly if Cloud save was disconnected, changed or signed out mid-save (a read asked for by `pullCloud` stops after the merge, as above). `sameCloud` compares `url`, `key` and `kind`, and runs again right after the PUT along with `ready` and the tab check, so nothing is put back once a sign out or disconnect has landed. Never write the main copy without that read and merge, or a stale tab replaces newer progress from another device.
  - `sendCloud` returns at once for an account while `Account.switching` (the account gets nothing until the move into it has merged), and leaves the tab if another tab signed in or out. On success it sets `Cloud.retry` back to 60 s, and for an account starts `uploadDue` and `retryHeld`. A failure goes through `cloudFailed`. Key mode tries again in a minute, as always. An account waits `Cloud.retry`, which doubles after each failure up to `APP.accountRetry` (10 minutes), so a site that's out of requests for the day isn't kept busy. The failure clears any timer a change set while the try was waiting for its answer, or that timer would fire first, and a server that never answers would get a try about every 74 s for as long as you type.
  - Every `Cloud.call` except a keepalive one gives up if no answer starts within `APP.cloudTimeout` plus 1 s per 10,000 characters uploaded. Once the answer starts, the body can take as long as it needs. This keeps one stuck request from holding up the queue without cutting off big uploads on slow links.
  - `state.devices` is `[{id, seen, left}]`, unioned by `mergeDevices` (max of each) and capped by `hydrate` at `APP.cloudDevices`, most recently seen first. Every save marks this browser as seen. Other browsers only read slots of listed browsers, so `init` saves right away when the cloud copy doesn't list this browser yet.
  - Tabs of one browser share its slot, so each tab folds in the other tabs' local saves through the `storage` event. Keep that listener, or a stale tab's local save or left copy drops another tab's tests.
  - Known limit. KV's delay between locations can drop a browser from the main copy's list (last write wins), and then its newest left copy waits until that browser opens again.
  - `ready` stays false until `init` has hydrated, so nothing can write DEFAULTS over a real save. Keep it that way. A tab that signs out or leaves sets it false again for good, which stops every save from that page.
- **`hydrate` is the one gate for every load.** That covers init, cloud connect, an account sign in (`adoptAccount`, and `clearLocalInPlace` with a deep copy of DEFAULTS), the merge inside `pushCloud`, another tab's local save (the `storage` listener), and backup restore and daily cloud copy restore (both through `restoreFrom`). It rebuilds state field by field and resets any setting whose `typeof` differs from DEFAULTS. It checks enums against include lists or lookup tables and clamps numbers. It caps history at `APP.historyLimit` (and its keystroke detail through `trimDetail`), `daily` and `clean` at 400 days, `removed` at 200 and pieces at twice `APP.writeMax` (only a merge can pass `APP.writeMax`, which `startPiece` enforces, and then the ones edited longest ago go). It clamps `welcomed` to a whole number of 0 or more, and a save with any test in any profile but no `welcomed` counts as welcomed (stamped with its `savedAt`), so saves from before the welcome need no version bump and never see it. It never updates `state.version`.
- **Migrations.** To change the schema, bump `APP.version` (currently 8) and add an `if (from < N)` block in `hydrate`. Version 8 moves saves that were on Words to Step up.
  - `from` is `Number(saved.version) || 1`. An object without `version` therefore runs every migration and has its unit, capitals, punctuation, word pool, theme and finger colors forced.
  - Always pass `hydrate` a parsed or `snapshot()` copy that still has `version`. Never pass live state, because `hydrate` clears each state field before reading the same field from its argument, which would wipe profiles, daily, clean and docs. It also keeps the argument's `keys` objects by reference (`cleanKeys` mutates and returns them).
- **New top-level fields.** A new state field goes in the initial `state` and in `hydrate`. If you miss `hydrate`, the saved value is silently dropped on every reload. `mergeSaves` starts from a copy of the newer save, so it only needs code if both copies' values should be combined. A page running older code drops any field it doesn't know when it hydrates, and writes the cloud copy without it. So a new field has to survive that, as `writes` does, since `mergeWrites` keeps a piece that only one side has, and the browser that wrote it puts it back with its next save.
- **Cloud save** (`Cloud`, `pushCloud`, the Cloud save subsection).
  - In key mode it sends bearer-key fetches to the user's Worker. Object names are the state and doc Store keys URL-encoded, plus one `keyprint-pending-<device>` slot per browser (`APP.cloudPending` is the prefix), `backups` and `backup-YYYY-MM-DD`. `keyprint-cloud` never leaves the browser. An account sends the same names to `/api/u/<name>` on the page's own origin, with the session token as the bearer, plus `keyprint-sync`.
  - Status 401 becomes `key`, 500 becomes `setup` and any other failure `reach`. A GET that returns 404 is null. For an account only, a 401 whose body is `Revoked` becomes `revoked`, and 413 and 507 become `full`. Key mode never reads a 401 body. `cloudProblem` passes `key`, `setup`, `revoked` and `full` through and turns everything else into `reach`.
  - One cloud per browser. `renderCloudStatus` hides `#cloudGroup` while an account is in use, says Cloud save is for people who run their own save Worker when it's off and accounts are available, hides the Daily copies row whenever Cloud is off (a session that ended included), and sets `#cloudDaysHint` by kind. `onCloudConnect` sets `kind` to `"key"` and drops a signed out marker, and `onCloudOff` empties `kind` and `cloudSeen`. Daily copy dates show as their UTC day.
- **The Worker side** (`save-worker.js`).
  - `SITES` lists the only origins allowed by CORS (`https://type.stevenwu.org` and the `typing.stevenhaochengwu.workers.dev` address). From any other origin, including a Claude artifact, a `file://` page or localhost, the browser blocks every response and the app reports `reach`.
  - Routes are `OPTIONS` (no key needed), `GET backups` (the daily copy days, newest first), then GET, PUT and DELETE on a name matching `/^[A-Za-z0-9._:-]{1,120}$/`. Doc names decode to `keyprint-doc:<id>`, which fits.
  - A PUT of `keyprint-state-v1` also writes `backup-<day>` if that day has no copy yet. The day is the UTC date, so outside UTC the "day" starts at a local time other than midnight (evening in the US). Daily copies are never deleted.
  - DELETE refuses the main state and daily copies (403). Bodies over 20,000,000 characters get 413. Missing `DATA` or `SAVE_KEY` gives 500, which the app shows as the setup message.
  - Workers KV is eventually consistent. A write can take 60 seconds or more to show up at other Cloudflare locations, same-key writes are limited to one per second (faster ones throw a 429 inside `put`), and the last write wins. Two devices are not guaranteed to see each other's latest save, which is why `mergeSaves` exists and why it must never drop data from either side.
  - A save merges the main copy unless it's the very copy this browser last wrote or read. `Cloud.mark` holds `copyMark` of that copy's exact text (`textMark` and its length), and `readCloud` and `readAccount` give the mark of what they read. It used to compare `savedAt` with `Cloud.seen`, and `savedAt` is each browser's own clock, so a browser whose clock ran ahead never merged what the others had saved and then wrote its own copy over theirs. Nobody's clock comes into it now. `init` merges the main copy and the left copies at start.
  - `keepalive` only applies to bodies under 60,000 characters, which is why the left copy is slim. Merging only ever adds tests, so leaving older ones out of it loses nothing.
- **The account service** (`site-worker.js`). Its constants sit at the top of the file, unit first in each comment.
  - Routing. Paths outside `/api/` go to `ASSETS`. Every `/api` answer carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and `Cross-Origin-Resource-Policy: same-origin`, and never an `Access-Control-*` header. OPTIONS gets 405, and a request other than GET whose `Origin` isn't the page's own gets 403 (`origin` on auth routes, `Not allowed` on data routes), so no other site can read or send anything. Without the `DIRECTORY` or `VAULT` binding, config still answers with `ready: false`, other auth routes give 500 `setup` and data routes 500 `Setup is not finished`. Anything else under `/api/` gives 404 `route`. Any throw is logged as `console.error("api", <route word>, err.name)` and answered 503 (`later`, or `Try again later`), never 500.
  - Formats. A username is `normalize("NFKC").trim().toLowerCase()` and must match `/^[a-z0-9][a-z0-9._-]{2,31}$/`, and a name in `RESERVED` answers as taken. A proof is 43 characters of base64url (32 bytes), and a uid 20 of `[a-z0-9]`. The token is `kp1.<uid>.<secret>`, returned once in a JSON body and sent only as `Authorization: Bearer`. An email address is normalized the same way, must match `EMAIL_RE` (the HTML email pattern, at most 254 characters) and is the name of its password login, so it can't be changed either. A username never holds an at sign, so `normalLogin` tells the two apart. An emailed code is six digits. The user JSON is `{id, name, username, email, login, google, password, called}`. `login` is what the password goes with, an email address or a username from before email, and empty with no password. `name` is the username, else `login`, else the email Google gave, else `Google account`. `email` is for display only (the address an email account was made with, replaced by Google's when Google is added). `called` is the name the account shows, or empty. It's kept in the account's Vault, not the Directory, and the Worker adds it to every user answer (`withCalled`). `normalCalled` tidies one. It's NFKC, with control and invisible characters out and single spaces, at most `CALLED_MAX` (40) characters, in any script, and it needn't be anyone's alone, since it isn't a way in. The two joiners (U+200C and U+200D) stay, since some scripts spell names with them and so do emoji made of parts, a lone surrogate goes, and a name with nothing to see in it (only fillers, joiners or combining marks) counts as no name. It's put in NFKC once more after the invisible characters are out, since taking one out can leave a letter next to a mark it joins with, so tidying a name twice changes nothing and the page holds what the Vault does.
  - Auth routes are JSON under `/api/auth/`. POSTs need `Content-Type: application/json` (otherwise 415 `type`), at most `BODY_MAX` (8,192) characters (413 `body`) and an object (400 `body`), and a wrong method gets 405 `method`. More than 60 auth POSTs a minute from one address get 429 `busy` with `retry` 60, counted in memory per Worker isolate. Errors are `{"error": "<word>"}`, and `busy` adds `retry` in whole seconds.
  - GET `config` gives `{v: 1, ready, google, googleAt, mail, write}`, with `google` the client ID when this origin is in `GOOGLE_ORIGINS` and `googleAt` the first listed origin when it isn't, `mail` true when the site sends email (`mailOn`) and `write` true when it makes Write's questions and word lists, and makes no Durable Object call.
  - Without a mail service, `signup {username, proof, called}` gives 201 `{token, user, created: true}` (`called` is optional everywhere it's taken, and the Vault keeps it with `session-new` only when the account has no name yet), or 400 `username` or `proof`, 409 `taken`, 429 `busy`, 429 `closed` (the day's cap) or 429 `full` (the site's ceiling). With one, `signup {email, proof}` makes no account. It keeps the password's hash and the hash of a code under the address for `CODE_LIFE` (15 minutes), emails the code and gives 202 `{sent: true}`, or 400 `email` (a username gets this too) or `proof`, 429 `busy`, `mails`, `closed` or `full`, or 503 `mail` when the email couldn't be sent. Asking again replaces the code and the password. An address that already has an account gets the same 202 and an email saying it has one, so the answer never tells who has an account.
  - `confirm {email, code, proof, called}` makes the account when the code and the same proof both match, and gives 201 `{token, user, created: true}`. The name comes with the code and not with `signup`, since no account exists until then. Anything wrong (a bad, used, expired or missing code, another password) gives 400 `code`, an address confirmed meanwhile 409 `taken`, and a code takes `CODE_TRIES` (5) tries before it's gone. `forgot {email}` always gives 202 `{sent: true}` for a well formed address and emails a code only when it has a password login, without waiting for the email (`ctx.waitUntil`), so neither the answer nor its timing says whether there's an account. `reset {email, code, proof}` sets the new password, ends every other session as a plain sign out (`session-new` with `sole`) and gives 200 `{token, user, created: false}`, or 400 `code`. All three give 404 `route` on a site without a mail service.
  - `signin {email, proof}` or `signin {username, proof}` gives 200 `{token, user, created: false}`, or 401 `wrong` for an unknown name and a wrong password alike, 403 `confirm` when the address has a sign up waiting for its code and the proof is that sign up's, 400 `email` or `username`, 429 `busy` or 503 `later`. It works the same with and without a mail service. `google {credential, proof, create}` gives 200, or 201 with `created: true` when it makes an account (which starts with the name in Google's token), or 400 `credential`, 401 `google` (any failed check, Google not set up here included), 429 `busy`, `closed` or `full`, or 503 `later` when Google's keys can't be fetched. With `create` false, which is how the page signs in, a Google account that's new to Keyprint gets 200 `{new: true, email}` and nothing else happens. No account is made, no sign up is counted and the nonce stays unused, so the same credential and proof sent again with `create` true make the account once the person has said yes. The question still counts as an attempt, and only a real `false` asks. With sign ups closed for the day or the site full it answers 429 `closed` or `full` in place of asking about an account it couldn't make. The limit of sign ups from one address only counts when an account is made. Without `create`, as a page from before this sends it, the account is made at once.
  - The routes that take the token are `signout {all}` (200 `{ok: true}`, revoking this session or, with `all`, every one), `link {credential, proof}` (200 `{user}`, 409 `linked` when that Google account has its own Keyprint account, 409 `has` when this one already has Google), `password {proof, old, username, email}` (200 `{user}`, with `old` the current password's proof for a change, 401 `wrong` when it doesn't match, or for a first password either `username`, or `email`, which must be the address Google vouched for on that account and needs no code, with 400 `username` or `email` or 409 `taken`) `name {called}` (200 `{called}` with the name as kept, an empty one taking it away, 400 `name` when it isn't a string, and 429 `busy` past the Vault's write limit) and `delete {confirm: "delete"}` (200 `{ok: true}`, 400 `body` without the confirm). Linking Google, adding a first password and deleting need a session made within `FRESH` (15 minutes) and get 403 `recent` otherwise, and the Directory decides that a password is a first one from its own logins, never from the body. Each of these gives 401 `session` for a malformed, unknown, idle or expired token and 401 `revoked` for a revoked one.
  - Data routes, `/api/u/<name>`, keep the save Worker's names, bodies and statuses, so `Cloud.call` works unchanged. A name must be `keyprint-state-v1`, `keyprint-sync`, `backups`, `keyprint-pending-<device>`, `keyprint-doc:<id>`, `keyprint-face` or `backup-YYYY-MM-DD` (`nameKind`), and anything else, or one that won't decode, gets 400 `Bad name`. GET gives the bytes or 404 `Not found`, and `backups` the day list, newest first. PUT works only on the main copy (up to `MAIN_MAX`, 8,000,000 bytes), left copies (`SLOT_MAX`, 262,144), texts (`DOC_MAX`, 12,000,000) and the picture (`FACE_MAX`, 60,000), answering 200 `Saved` or 413 `Too large` (before reading when `Content-Length` says so), and gets 403 `Not allowed` everywhere else. A picture must be a data URL of a JPEG, PNG or WebP image (`FACE_RE`) and gets 400 `Bad picture` otherwise. A byte order mark in front counts as otherwise too (the Vault decodes with `ignoreBOM`, which keeps it in the text), since stored with the picture it would make the mark differ from the one the page works out, and every read would fetch the picture again. DELETE works only on texts and the picture (200 `Deleted`, also when it was already gone) and gets 403 elsewhere. A method other than these gets 405 `Not allowed`.
  - Other data answers are 401 `Signed out` (no token, or an unknown, idle or expired session), 401 `Revoked`, 429 `Slow down` (more than `PUTS_MAX`, 120, writes in 10 minutes, counted in Vault memory, or the bad token limiter), 507 `Full` and 503 `Try again later`. A missing or malformed token is answered without reaching a Vault and isn't counted, since any page can send one from a visitor's browser. Only a Vault's 401 counts, and once one address has 20 of them in 10 minutes its data requests get 429 without reaching a Durable Object. Both in memory limiters hold at most 5,000 addresses and start over past that.
  - `keyprint-sync` is one read in place of 1 + N GETs per save, and never 404. Its body (`application/octet-stream`) is a JSON header `{"v":1,"main":<bytes, or -1 with no main copy>,"slots":[["<device>",<bytes>], ...],"called":"<name>","face":"<mark>"}`, one `\n`, then the main copy's bytes and each left copy's in header order, newest written first, at most `SLOTS_MAX` (24). A new left copy past 24 drops the one written longest ago. The Vault copies stored bytes into the frame without decoding them, and `readAccount` splits it. `called` and `face` are the name the account shows and the mark of its picture, both empty when it has none, so a change made in one browser reaches the others with a read they make anyway. The mark is `faceMark`, an FNV-1a hash of the picture's bytes and their count, which the page works out the same way for the copy it holds, and a browser fetches `keyprint-face` only when the two differ.
  - Daily copies. The first main copy PUT of each UTC day is copied to `backup-<day>` inside SQLite, in the same transaction, and only the newest `KEEP_DAYS` (14) stay, where the save Worker keeps every one.
  - Budgets. An account keeps `ACCOUNT_BYTES` (40,000,000) in all, daily copies included, or `YOUNG_BYTES` (4,000,000) for the first `YOUNG` (3 days) after it's made. Texts also have caps of their own, `DOCS_BYTES` (24,000,000) in all and `DOCS_MAX` (200). A text, a left copy or a picture past any of these gets 507. The main copy is never refused for them. The oldest daily copies go to make room instead, and once that isn't enough, today's is skipped.
  - The site's ceiling. Each Vault tells the Directory its size whenever it has grown or shrunk by `STEP` (1 MiB) since the Directory last heard (`meta.reported`), and the Directory keeps a `sizes` table and their sum. Past `SITE_BYTES` (4,000,000,000) the Directory refuses growth and new accounts (429 `full`). Then texts and left copies get 507, and a main copy is saved without its daily copy, or gets 507 when even that would grow the account by more than `STEP`. A Directory that can't be reached fails texts and left copies with 503 and never holds up a main copy. Deleting an account takes its size out. `SELECT * FROM sizes ORDER BY bytes DESC` in the Directory shows the biggest accounts.
  - Durable Objects. One `Directory` (`idFromName("directory")`) keeps `users`, `logins` (`pw:<email or username>` with salt, hash and alg, or `g:<sub>`), `limits`, `used` (Google nonces already taken), `codes` (emailed codes waiting to come back), `sizes` and `meta` (the key for hashing addresses and codes, the day's counts of sign ups, emails and word lists, the last prune and the site's bytes). One `Vault` per account (`idFromName(uid)`) keeps `meta` (`uid`, `created`, `reported`, `called` and `face` when the account has a name or a picture, and after a delete, `deleted`), `sessions` (the SHA-256 of each secret, with `created`, `seen` and `revoked`) and `blobs` (each name in parts of `PART`, 1 MiB). The Worker reaches them only through POSTs to `/internal/<route>` that it builds itself (`signup`, `pending`, `confirm`, `forgot`, `reset`, `wrote`, `signin`, `google`, `link`, `password`, `remove` and `size` on the Directory, `session-new`, `check`, `fresh`, `called`, `end`, `end-others` and `delete` on the Vault) and the Vault's `/data/<name>`. `check` and `fresh` answer with `called` too, which is how the token routes that answer with a user get the name.
  - Sessions last `IDLE` (90 days) without use and `LIFE` (400 days) at most, `seen` moves at most once a day, and an account keeps `SESSIONS_MAX` (20) live ones, so a new one pushes out the least recently seen. Sign out, Sign out everywhere and Delete account set `revoked`, and those rows stay until `created + LIFE`, so a browser that comes back much later is told `Revoked` and clears itself. A password change deletes the other live sessions instead, so those browsers see `Signed out`, keep their progress and merge it back when they sign in again. A password reset does the same to every session but the new one. Delete removes the user, logins, blobs, name and picture at once, and the Vault's alarm removes the rest after `LIFE`.
  - Passwords never leave the browser. It sends `passwordProof`, PBKDF2-SHA256 of the NFKC password with the salt `keyprint:v1:<login>` (the email address or username it goes with) and `APP.passwordRounds` (600,000) rounds. The Directory stores an HMAC of that proof with 16 random bytes of salt per login (alg `kp1`), or keyed with `PEPPER` when it's set (`kp2`, and a `kp1` row is rehashed at its next sign in), and compares in constant time. An unknown username runs the same HMAC and answers like a wrong password. The rules the server can't check are in `passwordProblem` (at least `APP.passwordMin` characters, and for a new password not the email address or username, not in `EASY_PASSWORDS` and not one character repeated), and the fields stop at 200 characters.
  - Google. `verifyGoogle` checks an RS256 ID token against Google's published keys by `kid`, then `iss`, `aud` and `azp`, `exp` and `iat` with a little skew, `sub`, and a `nonce` that must be the SHA-256 of the proof sent beside it, which only the page that started the attempt holds. The Directory takes each nonce once (`spend`), except that a question about a new account (`peek`) checks it and leaves it for the answer. Accounts are matched by `sub` only, never by email, which is kept for display when Google says it's verified. A failure logs one reason word, never the token.
  - Limits, exact because the Directory is one strongly consistent object. Sign in and Google attempts count 120 per 10 minutes per address. After 5 wrong passwords for one username from one address, the next try waits 15 s, doubling up to 15 minutes, and each username takes 50 attempts an hour from all addresses. Sign ups take `SIGNUPS_PER_PLACE` (30) in 24 hours per address (then 429 `busy`) and `SIGNUPS_PER_DAY` (500) in a UTC day across the site (then 429 `closed`). An IPv6 address counts by its /64 for attempts and its /48 for sign ups. Addresses are kept only as keyed hashes, for at most a day. Emails take `MAILS_PER_ADDRESS` (5) an hour to one email address, `MAILS_PER_PLACE` (10) an hour asked for from one address (both then 429 `busy`) and `MAILS_PER_DAY` (90) in a UTC day across the site (then 429 `mails`), counted before anyone learns whether the address has an account. A try at a code counts toward the 120 per 10 minutes too.
  - Email. `sendMail` posts to Resend with `RESEND_API_KEY` and `MAIL_FROM`, as text and plain HTML, with a 10 s limit. `mailCopy` has the three emails, `confirm`, `reset` and `have`, with the code in the subject and no links. Codes are kept only as keyed hashes (`codeHash`, with the Directory's own key) in the `codes` table, under `s:<email>` for a sign up and `r:<email>` for a reset, and `codeGate` counts each try before the code is checked.
  - Write. `POST /api/write/field {prompt, text, lang, ask}` with the session token gives 200 `{words: [...], questions: [...]}`. `questions` are the ones the piece's warm-up asks, which guide the person's thinking about what they're about to write, `ask` of them (between `WRITE_ASKS_MIN`, 6, and `WRITE_ASKS_MAX`, 16, and `WRITE_ASKS`, 12, when the page doesn't say). `words` are the entries a model suggests for the piece, at most `WRITE_LINES` (150). Both come from one call to the model, so a piece costs one of the day's lists, as it did when it had only words. `fieldParts` splits the answer, a line with a question mark in it (English or Chinese) being a question of at most `WRITE_ASK_CHARS` (240) characters and every other line an entry, each cleaned of list marks (`LIST_MARK`, a bullet, the hashes of a heading or a number with its mark or a dash, so a line that starts with a year keeps it) and bold marks. A heading is left out, which is a line that starts with a hash and asks nothing (a question a model wrote as a heading is still a question), one that ends in a colon, or one that only names the part that follows (`FIELD_HEAD` through `fieldHead`, which takes accents off first, so Questions, Vocabulary or Key words, say) ahead of the first entry. A line or two ahead of the first question is the model saying what follows, so those aren't entries either. The page cleans both again for what the keyboard can type (`cleanAsk`, `cleanEntry`), and splits an answer the same way where it asks Claude itself (`fieldSplit`, which must stay the same as `fieldParts`). `askWords` gives the model the task in `writeTask(asks)`, with `WRITE_FIRST_FORM` or `WRITE_FIRST_FORM_ZH` for how to lay the answer out (a Chinese question has a space between its words, then a bar and the pinyin of every character), and the person's words inside `piece` and `document` tags, cut to `WRITE_PROMPT` (600) and `WRITE_TEXT` (24,000) characters, and the document also to `WRITE_BYTES` (30,000) bytes of UTF-8 (`fitBytes`, on a whole character), so a Chinese text at three bytes a character costs no more to read than an English one, with a 25 s limit. Without the `ANTHROPIC_API_KEY` secret, as on the site now, `askAI` runs `WRITE_AI` (`@cf/zai-org/glm-4.7-flash`, chosen for its price and its Chinese) through `env.AI.run` with thinking off (`chat_template_kwargs`), at most `WRITE_AI_TOKENS` (1,500) tokens and messages in the chat form. `aiText` reads the answer from `choices[0].message.content` or the older `response` string, drops anything inside think tags, and drops the last line of an answer that stopped at the token limit (`finish_reason` `length`), which ends in the middle of an entry. The time limit is an `AbortSignal.timeout` passed to the binding as `{ signal }` in its third argument, with a race beside it for a runtime that doesn't stop. A call that throws logs the Workers AI error code from the start of its message, or the error's name without one. 3036 is the day's allowance used up and 3040 no capacity, which pass. 5028 is a retired model and 5035 one that needs a paid plan, which mean `WRITE_AI` has to change. With the secret, `askClaude` asks `WRITE_MODEL` (`claude-haiku-5-5`, at low effort) through the Messages API instead, and reads the answer's text by block type, since it can start with thinking blocks. With neither the binding nor the key (`writeOn`) the route gives 404 `route`. It gives 401 `session` or `revoked` like the other token routes, 400, 413 and 415 like the auth routes (with `WRITE_BODY`, 40,000 characters), 429 `busy` with `retry` after `WRITE_PER_DAY` (20) lists in 24 hours for one account, 429 `closed` after `WRITE_SITE_DAY` (1,000) in a UTC day across the site (the Directory's `wrote` counts both before the model is asked), 422 `refused` when the model declines (an open model that declines in plain words reads as a short answer instead), and 503 `later` for anything else, a used up Workers AI allowance included, and an answer with fewer than 8 entries and fewer than 3 questions, which logs `short`. Either part alone is worth sending, since the page has general questions and the person's own words to stand in for the other. With `sofar` in the body, what has been written of a piece that's under way, the list follows the writing. `askWords` then gives the model `WRITE_MORE_TASK`, with `WRITE_FORM` or `WRITE_FORM_ZH` for entries alone, and the words inside `piece` and `written` tags in place of a document (any `text` and `ask` are ignored, and the answer has no `questions`), where `sofar` is the newest `WRITE_SOFAR` (2,400) characters and at most `WRITE_SOFAR_BYTES` (3,600) bytes of them (`fitBytesEnd`, which cuts from the front), asks for about `WRITE_MORE_WORDS` (30) entries in at most `WRITE_MORE_TOKENS` (800) tokens from Workers AI (Claude, on a site with a key, keeps the limit it has for every list), and takes 5 entries as enough. `sofar` alone is enough to ask with. The Directory's `wrote` counts these apart, `WRITE_MORE_DAY` (100) in 24 hours for one account under `x:<uid>`, since a piece asks for several as it grows and each costs a fraction of a first list. They have a day of their own for the site too, `WRITE_MORE_SITE_DAY` (3,000, the count `mores` in `meta` beside `writes`), so however much people write, nobody's first list is refused for it. What really bounds them is the Workers AI allowance, which first lists share. `tidy` takes the three tag names out of what was sent however they're spaced, so nothing written can close the tag it sits in. A page from before this sends no `sofar` and gets a first list, as it always did, and a page from before questions reads only `words` from an answer. The budgets count lists, not what they cost, so `WRITE_BYTES` and `WRITE_AI_TOKENS` are what bound a list's cost (see Workers AI under Deploying). Workers AI is free within the allowance. At Haiku's price a list would cost well under a tenth of a cent, so the site's cap would be under a dollar a day.
  - Cost. On the Free plan only `/api` and paths with no file count toward the 100,000 Worker requests a day, and an active person makes roughly 85 (each save is `keyprint-sync` and a PUT, at most one save a minute while they practice, and coming back to the page adds one read at most every two minutes). Once a limit runs out, `/api` answers 429 or 503, pages still load, practice saves in the browser and the app backs off. `APP.accountDelay` and `KEEP_DAYS` (with its hint) are the first levers.
  - Known limits. Two devices saving in the same instant can still drop one device's newest tests from the main copy, and they come back from that device on its next save. A tab open from before a deploy runs old code with no account listeners. An email account gets back in with Forgot password. An account that signs in with a username from before email still has no reset, so adding Google is its way back in. An email address can't be changed, and a username account can't add one. Progress typed in a browser before signing in joins the account with no question, so on a shared computer someone else's tests can end up in it, and the note after the sign in is what says so. A name typed while creating an email account is gone if the page reloads before the code comes back, and can be added in Settings afterwards.
- **Account mode** (the Accounts in the save pipeline subsection and the Accounts subsection).
  - `Cloud.kind` is `""`, `"key"` or `"account"`. `Cloud.user` is the account this browser's progress belongs to, kept after its session ends, and `Cloud.retry` is the account's backoff. For an account `Cloud.url` is `accountBase()` (the page's origin plus `/api/u`) and `Cloud.key` the token. `Cloud.on` is still `url && key`, so an account whose session ended is off but keeps `kind` and `user`.
  - The pipeline is the same, name for name. `readCloud` calls `readAccount`, one GET of `keyprint-sync`, so a save is two requests. `readAccount` checks the whole frame before it takes anything from it (`v` 1, `main` a whole number from -1 up, `slots` a list, and every size within the bytes that came), and a frame that's wrong in any way is a failed read (`reach`), never an empty account that the next save would write over. The name and the picture in the header are only taken once the whole frame has read well. Left copies go to the account's own `keyprint-pending-<device>`.
  - `Account` holds the account UI and tab state. `conf` is what `/api/auth/config` offered, `marker` the signed out marker, `due`, `held` and `heldAt` the text lists, `pending` a sign in waiting on the merge row's question (`{token, user, created, via}`, or `{fresh, via, credential, proof, email}` for a Google account that has no account yet, which only ever lives in memory), `busy` an action running, `switching` progress moving between clouds (which pauses this tab's identity checks and its account saves), `leaving` a tab that's reloading and never saves again, `message` an error, a step hint or a piece of news shown in place of the note (`{text, warn, once}`, see The Account group shows one thing at a time), `note` and `toast` what the first start after a sign out shows, `proof` the secret behind the current Google nonce, `gis` Google's script (0 not loaded, 1 loading, 2 ready, 3 failed), the `*Armed` timers of the buttons that take two clicks, `createStep`, set while Create account waits for the password a second time and for your name (`#accountPass2Row` and `#accountCalledRow`, which `endCreateStep` hides and empties), `step`, `stepEmail`, `stepProof` and `stepCalled` while the form waits for an emailed code (see below), `face` (`{user, mark, data}`, the picture this browser holds and whose it is), `faceBusy` while a picture or a removal is on its way up, `faceFetch` while another device's picture is on its way down (which never holds up an upload or a removal, and drops what it brings when a picture was set here after it began), `faceTry` (`{mark, data}`, a picture sent or removed whose answer didn't come, which a read that shows that mark takes as done, warning and all), `calledAt` and `faceAt` (when the name or the picture was last set here, or taken from another tab, by `performance.now()`, so a read that began before can't put the old one back) and `pulledAt` (when the account was last read, in ms, for `pullCloud`).
  - Email or username. `mailMode()` is `Account.conf.mail`. With it, the name field is labeled Email, Create account takes only an email address, and Forgot password shows. Without it the form is the username form, word for word as before. Sign in is the same either way. A name with an at sign goes as `{email}` and anything else as `{username}`, so usernames from before keep working on a site with email.
  - The code step. After `signup` answers 202, or `signin` answers 403 `confirm`, `beginStep("confirm", email, proof, note)` shows only the code field with Confirm, Send a new code and Cancel. The proof stays in memory (`Account.stepProof`), never in storage, so a reload goes back to the form, and signing in with the same password brings the step back. Forgot password starts `beginStep("reset", ...)`, which shows the code and two new password fields. `onStepOk` sends `confirm` or `reset` and hands a 200 or 201 to `askAboutProgress`, like any sign in. `renderAccount` sets what shows from `Account.step`.
  - A Google only account adds its first password under the address Google vouched for (`firstPasswordEmail`), with no username and no code, when the site has email and Google gave a verified address. Otherwise it takes a username, as before.
  - Name and picture. They belong to the account and not to the progress, so they live in the Vault's `meta` and in `keyprint-face`, and never in the state blob, a backup or a daily copy. `Cloud.user.called` is the name. `calledOf` is what the page calls an account (its name, else what it signs in with), `firstName` is for the sign in toast, and `initialsOf` gives the letters on the key cap, the first letters of the first and last words of the name (SW for Steven Wu), one letter for a name of one word, or the first letter of the login with no name. A letter is a whole character as a reader sees it (`firstGlyph`, with `Intl.Segmenter` where the browser has it), so a flag, an emoji made of parts or a letter with its marks stays whole, invisible characters at the start of a word are skipped, and a capital that's two letters (ß to SS) gives the first. Two letters fit on the cap and an emoji is about as wide as two, so a name that starts or ends with one shows only its first, and `.who` never wraps. Create account asks for the name in the same step as the second password, and it can stay empty. A username sign up sends it with `signup`, an email one keeps it in `Account.stepCalled` and sends it with `confirm`, and a new Google account starts with the name Google has. The who row at the top of the panel changes it through `auth/name` (`onWhoSave`).
  - The picture is whatever image the browser can read, cut to its middle square and drawn `APP.faceSize` (128) px wide on a white ground by `makeFace`, then kept as a JPEG data URL of at most `APP.faceMax` characters (it tries three qualities), so nothing else the file carried is kept. A file the browser won't let a page read back, like an SVG drawing that holds a foreignObject, throws at `toDataURL` and gets the same message as a file that isn't a picture. `onFacePicked` PUTs it to `keyprint-face` and `onFaceDrop` DELETEs it, and `faceFailed` words a failure. `keepFace` holds it in `Account.face` and in this browser's `keyprint-face` key. Every `readAccount` hands the header to `noteProfile`, which takes a changed name and, when the header's mark isn't the one held, fetches the picture (`fetchFace`) or drops it, so both reach other browsers with their next read and cost no request of their own until something changed. Other tabs of the same browser follow through the `storage` event (`joinCalled` for the name in the config, and the `keyprint-face` key), and each raises `calledAt` or `faceAt` when it takes a change, or a read that tab began before the change would put the old name back and remove the picture in both tabs.
  - The key cap. `renderWho` shows `#who` at the end of the top bar whenever this browser's progress belongs to an account (`Cloud.kind === "account"`, a session that ended included), with the picture or the initials (`fillWho`, which redraws only when what it shows changed), a dot (`.warn`) when the sign in ran out or the account can't be reached (`reach` or `setup`), and a `title` and `aria-label` saying who's signed in and when it last saved. A click goes to Settings and brings the Account group into view. The bigger one in the panel is `.who.big`.
  - `accountPlace()` says where accounts work. It gives `claude`, `file`, `frame`, `insecure` or `none`, each with a note in the Account group, or `ok`. `loadAccountConfig` asks `/api/auth/config` once per page, with an 8 s limit, when Settings first opens. No answer, a 429 or a 5xx asks again next time, and a 404 or a reply without `v: 1` means this address has no account service.
  - `cloudFailed(err)` notes a failure and says whether to try again. In key mode it only sets `Cloud.error`. For an account, `revoked` runs `clearBrowser("revoked")` on a timer (so `sendCloud` can call it), `key` runs `sessionEnded` and stops, and anything else is noted and retried. `sendCloud`, `sendDoc`, `init` and `onCloudRestore` send every failure through it, and `loadCloudDays` and `uploadDue` only an ended or revoked session.
  - `sessionEnded` keeps the progress here and stops every request. It empties `Cloud.key`, `error`, `mark` and `lastOk`, keeps `kind` and `user`, and saves the config, unless another tab has already signed in again, when it leaves instead. The Account group then offers to sign in again (the same account merges without asking) or Clear this browser.
  - `settleCloud` cancels a waiting save and the retry timer and waits for the running one, ignoring its failure, which is the next owner's to retry. Signing in, signing out and deleting run it before they switch or ask the server.
  - Texts. `cloudDoc` keeps each PUT in `textSends` until it settles. A failed account PUT lists the text in `Account.due`, or on `full` holds it (`holdText`, with the No room toast), and saves the config. `uploadDue` sends due texts one at a time in the background (asking during a run hands back that run). It never undoes a sign in, and it stops at the first failure other than `full`, so the next save that works tries again. Held texts are only in this browser, and `retryHeld` puts them back on the due list once `APP.heldRetry` (a day) has passed since `heldAt`, or at once after a removed text frees room. `settleTexts` waits for `textSends`, joins the other tabs' lists, runs `uploadDue` (twice when a run was already going) and says whether every text is up. `restoreBackup` lists every text as due when its upload fails.
  - Tabs of one browser share the config, and each one only knows the texts it tried. `joinTextLists` folds the stored lists for the same account into this tab's on every account `saveCloudConfig` and on the `storage` event, apart from the ids this tab just settled (`saveCloudConfig(settled)`). A text in both lists counts as held, so a big text isn't sent again with every save.
- **Tabs, signing in and signing out.**
  - `cloudIdentity(raw)` turns a config into whose progress it stands for, `none`, `key`, `account <uid> <token>` or `out <ms>`. `accountChange(a, b)` is true when two differ and either is an account or a sign out, so connecting or disconnecting key Cloud save, or a device id written at start, never reloads other tabs. `readConfigNow()` reads the stored config straight from localStorage.
  - The identity check compares `cloudIdentity(cloudSeen)` with `cloudIdentity(readConfigNow())`. A change means another tab signed in or out, so this tab's progress may belong to someone else, and it calls `leaveTab`. `saveLocal`, account writes in `saveCloudConfig`, `sendCloud` (before reading and again after its PUT), `sessionEnded` and `adoptAccount` (between its steps) all check, and so does the `storage` listener for `keyprint-cloud`. That listener also leaves when another tab removes `keyprint-state-v1` while this one is on an account, and a `pageshow` from the back forward cache checks again.
  - `leaveTab` sets `Account.leaving`, sets `ready` to false, clears the save and cloud timers and dirty flags, and reloads after 300 ms. It never saves first.
  - `adoptAccount(result, keep)` is the one path for every sign in, new account and Google sign in, and nothing changes until the account has been read. `keep` is false only when the progress here belongs to another account, which is cleared. Otherwise what's here joins the account. With key Cloud save on (`moving`) it first does a last `pushCloud` to the save Worker, and `fetchCloudDocs` then pulls texts that only that cloud has, so the save Worker has everything and the account gets everything. A failure there stops with nothing switched. Then `settleCloud`, the switch in memory and `readCloud` (a failed read puts `Cloud` back). The config is written next, before anything local changes, so other tabs stop first. Then it clears this browser unless `keep` (`clearLocalInPlace`, which also marks the test on screen as counted, so `newLesson` never adds its keys to the account, and drops `weakCache` and `weakMarkCache`, so the keys named from the progress that went don't carry over), empties `here.devices` (left marks from another cloud would make `foldLeft` skip real slots), merges with `mergeSaves(theirs, here, true)` so the account's settings and open text win and every test stays, folds the left copies in and hydrates. The screen follows in the same step, `afterMerge` and `newLesson` right after `hydrate` with no await between them. Until it does, the piece or the test on screen is the one from before the sign in while everything behind it is already the account's, and words typed into a piece in that gap went into the wrong piece or nowhere. Only My text can wait, for a text that isn't in this browser yet, and its test starts after `openDoc` when there's still none. It then stamps `welcomed` when that's still 0, since whoever signs in has used Keyprint here, so the welcome doesn't open again for an account with no tests yet (after a sign out and a new account, say). When a guest's progress joins, it first takes the account's `resetAt` per layout and `restoredAt` 0, so a Reset progress or restore made here before isn't one of the account's. Progress moving over from key Cloud save takes the account's resets too. It used to keep its own, and a Reset progress there that was later than the account's tests then took those tests, the account's letter stats and its unlocked letters away on every device, with a note that said only that the progress had joined. Tests here from before the account's last Reset progress on their layout were never part of what that reset cleared, and a merge drops a test older than a reset. So each of them gets `at`, when it joins (now, or one past the reset), which `mergeSaves` counts in place of `ts`. The account's reset itself stays where it is, so a device that hasn't heard of it yet still brings nothing back that it cleared, tests, letter stats or unlocked letters. (An earlier version moved the reset back and stamped `restoredAt`, and a stale device then brought back the letter stats the reset had cleared.) A page from before `at` existed still drops such tests when it merges, and they come back with the next save from a page that has them. Texts the account doesn't list become due, and it saves locally, pushes and starts `uploadDue`. Since nobody was asked, the note then says once what came along (`brought`, counted with `localProgress` after the last save to the save Worker, and worded by `progressText`), `The progress that was in this browser, 2 tests and 1 text, is in your account now.` or `Your Cloud save progress, ..., is in your account now. Your save Worker keeps its copy.` The toast is `Welcome, Ada` for a new account with a name and `Welcome back, Ada` for a sign in, or Account created and Signed in without one. If another tab signs in or out meanwhile, `giveUp` puts `Cloud` back, signs the unused session out and leaves, writing nothing.
  - `askAboutProgress` decides whether to ask first, and mostly doesn't (the owner asked for signing in to add what's here by itself). The same account after its session ended merges without asking. Progress that belongs to no account, a guest's or key Cloud save's, joins the account with no question, and so does an empty browser. Two things still ask, through the merge row (`#accountMerge`, with `#accountKeep` and `#accountCancel`). A Google account new to Keyprint always asks (the New account row with Create it and Cancel, whose hint says what progress here joins it), so nobody lands in a second, empty account without knowing. It asks before any account exists. `onGoogleCredential` signs in with `create` false, and on `{new: true}` `askToCreate` keeps the credential and proof in `Account.pending` and shows the row. Create it sends them again with `create` true (`createPending`) and hands the answer to `adoptAccount`, also when someone made that account elsewhere meanwhile and it comes back as a plain sign in. Google's credential lasts an hour, so a question left open longer says to try Google again. A passing failure (no answer, a 5xx or 429 `busy`) keeps the question, since nothing was made and the credential is still good, and says Keyprint couldn't be reached. A Google credential that comes while a question is open answers that question first, as Cancel would, so its session isn't left behind. Progress from another account, one whose session ended here, is never merged into someone else's account, so it gets Remove it and sign in, which takes two clicks, and Cancel, and with nothing of theirs left here it signs in at once. Cancel signs the new session out. For a new Google account there's no account and no session yet, so it only forgets the credential, and that Google login stays free to add to an account you already have. The account used to be made first and deleted on Cancel, and that delete could take away an account that another device, or a second click, had signed in to while the question was open, along with the progress that had just joined it. Never go back to making something Cancel has to delete. It also puts the form back as it starts (`endCreateStep`), since an account that Create account made a moment ago exists either way. There's no way to leave a guest's progress out any more. Reset progress before signing in is the way to start an account without it.
  - `clearBrowser(why)` is the only way progress leaves this browser. Sign out, Sign out everywhere, Delete account, Clear this browser and a `Revoked` answer all end in it. It sets `leaving` and `switching`, sets `ready` to false, stops every timer, calls Google's `disableAutoSelect`, writes the signed out marker, then runs `wipeLocal` (`keyprint-state-v1` and every `keyprint-doc:` key, keeping the config and its device id) and reloads. The marker goes first, so every other tab stops before anything is removed. It never waits on the cloud queue, so a cloud save can call it.
  - `finishSignOut` runs in `init` while the marker is `fresh`. It wipes again, because anything there now came from a tab that hadn't stopped yet, sets `fresh` to false and saves the marker (its identity doesn't change, so no tab reloads), and sets the toast and, after `revoked`, the note.
  - Sign out (`onAccountOut`) first saves locally, pushes, settles the texts and checks for held ones. If the account doesn't have everything yet, the button arms as Sign out anyway with a warning, and the warning goes when the button disarms. Then come `settleCloud`, the signout call (best effort for a plain sign out, required for Sign out everywhere) and `clearBrowser("out")`. Delete account runs `settleCloud` first too, so a running save can't come back `Revoked` and clear the browser before the delete answers.
  - `init` reads the config before `Store.load()`, runs `finishSignOut` when the marker is fresh, and clears the browser before drawing anything when the start read answers `Revoked`. A `key` answer keeps the local progress and shows the ended note. It stops before `ready` if the tab is leaving, fills the Cloud save inputs only in key mode, starts `uploadDue` when texts are due, sets `#savedNote` through `renderSavedNote`, opens the welcome only when there's no signed out marker (see The welcome) and shows `Account.toast`.
- **`mergeSaves`.**
  - History is unioned by `ts|wpm`, keeping only entries at or after the later `resetAt`, each counted from the later of its `ts` and its `at`. When both copies have a test, the one with `tx` wins, so a slim left copy never strips a test's keystrokes.
  - When both copies share a `resetAt`, each letter keeps the copy with the larger `n`, and `unlocked` takes the max. Otherwise the copy with the later reset wins both.
  - `daily` and `clean` take the max per day, not the sum.
  - `step` takes the later day's. On the same day it takes the copy with the later `at`, so a step down holds against a copy that grew earlier (taking the larger, as it used to, would undo every step down the next time a cloud copy or another tab merged in). Since `finishLesson` always puts `at` past the step it replaces, a change made after a copy merged in beats that copy however the clocks differ. Two changes made without seeing each other are ordered by their clocks. When either copy has no `at` (0), as in a save from before it was timed, the larger `words` wins, as before.
  - `welcomed` takes the larger of the two, so closing the welcome on one device counts on every device. Backups, restores and the slim left copy carry it like any other field.
  - `keepMine` keeps the local settings, `drillBack`, `docId` and `writeId`.
  - Pieces from Write go through `mergeWrites`, which never drops what either side wrote. For the same piece, `editOrder` compares the two `v` maps. A copy with every edit of the other and more is simply newer, whatever the clocks say. When each has edits the other lacks (two devices that wrote without seeing each other), or the counts are equal and the words differ (two tabs), the one with the later `edited` keeps the piece's id and the other is kept as a new piece titled with `(copy)`, unless its words are all still at the start of the winner's. The copy's id comes from the piece's id and a hash of its text (`textMark`), so every browser makes the same copy once and more merges add nothing. The winner takes the larger of each edit count, and keeps the other copy's `asks` when it has none of its own, so a page from before pieces had questions never loses them for the rest. The piece kept as a copy gets them the same way. A piece in `removed` stays out, and so does a removed copy.
  - A restore (backup file or daily copy) goes through `restoreFrom(copy)`. It merges the copy into what's here, with the copy's settings and open text taking over, and stamps `state.restoredAt` (and `savedAt`) with now. When two copies have different `restoredAt`, `mergeSaves` first runs `undoResets` on the copy restored less recently, which makes its resets from before the newer restore stop counting. Nothing else is trimmed, so a restore only ever brings things back. That's how it undoes a Reset progress another browser had already synced, without wiping a browser that connects later or work done after the restore. `restoredAt` is capped at a few minutes past now, in case a clock runs fast.
- **Backups** are `{app: "keyprint", version, savedAt, state, texts}`. Restore keeps the texts already here, adds the backup's, and drops a backup text whose words are missing from `texts`. A removed text stays removed, since `removed` is unioned everywhere. With Cloud on, a restore uploads the texts and pushes, and for an account a failed upload lists every text as due. Backups never hold the token.
- **Docs.** Doc ids must match `/^[a-z0-9]{4,40}$/`, or `hydrate` silently drops the document. Changing `APP.mergeWords`, `splitWords` or `pieceWords` moves saved `doc.at` positions onto different passages.

## Conventions

- **Code.**
  - Two-space indent, double quotes, semicolons, trailing commas in multi-line literals, `const` and `let`, template literals and arrow callbacks.
  - Use function declarations for real logic and one-line arrow consts for tiny helpers.
  - Names are UPPER_SNAKE for tables, PascalCase for singletons (`Store`, `Cloud`) and camelCase otherwise.
  - Short local names are normal, such as `s` for settings, `p` profile, `L` lesson, `k` letter stats, `ch` char and `P` palette.
- **DOM.**
  - Build elements with `node(tag, cls, text)` and `replaceChildren`, and hide them with the `hidden` property.
  - Show state through classList toggles that CSS reads.
  - Delegate clicks with `closest("button[data-...]")` and go through `el` for element refs.
  - To restart an animation, remove the class, run `void el.offsetWidth`, then add the class back.
  - Destructive buttons take two clicks, with a changed label and a 4000 ms disarm. Reset progress and Restore this copy add an `armed` class, and a text's Remove button sets `data-armed`. The account buttons (Sign out everywhere, Delete account, Clear this browser, Remove it and sign in) go through `armAccount`, which does both, with `data-armed` set to `again`. Sign out arms as Sign out anyway (`data-armed="anyway"`) only after its save didn't get everything up, and its warning goes when it disarms.
- **CSS.**
  - Colors come from custom properties (the red to green skill ramp in computed `hsl()` is the exception), and themes only redefine variables. Short rules go on one line.
  - Numbers use `tabular-nums`. Figures put `<dt>` before `<dd>` and flip them with `column-reverse`.
  - Classes are short and hyphenated, and state classes are single words. Ids are camelCase, apart from `view-*`, settings inputs `set-*` (except `sdSettings`) and readouts `out-<settingKey>`.
  - Every `<button>` has `type="button"`.
- **Comments.**
  - Write plain full sentences ending in periods, often in the second person, explaining intent above the code. Trailing inline comments are short lowercase fragments.
  - Empty `catch` blocks say why they are empty.
  - Section headers are `/* N. Name ---- */`, padded with dashes to about column 80, and subsections have no number. `site-worker.js` has only numbered sections (twelve), since the dev kit's static check takes any other run of dashes in it for a double dash.
  - In APP comments the unit comes first (`// ms between saves`).
- **UI copy.**
  - Use sentence case, second person, short and friendly wording. Contractions are welcome.
  - Full sentences end with a period. Button labels, button states and short toasts don't ("Start over", "Backup downloaded").
  - Feature names are capitalized like proper nouns ("My text", "One mistake restarts", "Text only").
  - Numbers go through `toLocaleString("en-US")` ("1,000"). Negatives use the Unicode minus, gains get an explicit +, and speed units come from `unitLabel()`.
  - Join a label and its value with a comma ("Speed now, 80% of target").
- **Punctuation.** No colons, no double dashes and no em or en dashes in UI copy or comments. That covers the emails in `mailCopy` and the tasks given to the model in `writeTask` and `WRITE_MORE_TASK`, which is why they name their tags in words and never write a label followed by a colon. The only runs of dashes are the section header rules. Use periods, commas or parentheses instead. The owner dislikes colons and double dashes in prose generally, so follow the same rule in docs and commit messages.
- **Internal ids differ from UI names.**
  - `step` is Step up (`stepWords()` gives today's length from `stepStart` and `stepTop`, and `finishLesson` grows or shrinks it before making the next test), `stepDown` is Down after (the mistakes that take a word away), `custom` is My text, `write` is Write (and `writeWarm` its Warm-up, in minutes), `suddenDeath` is One mistake restarts, `emulate` is Follow key positions, and `weakBoost` is Extra practice for weak keys, which covers letters, marks and digits.
  - Step up is the default mode, but the Practice page never names it (the owner asked for the label to go). In English Step up and Words `#focus` is hidden, and the keys getting extra practice are only outlined in the two rows above the text (see Weak keys). The owner asked for the line that named them to go, since the outlines already say it. Chinese Step up shows the same "Chinese, N words" line as Chinese Words. Only the word count under the text, the mistake dots beside it and the tags above the text ("Perfect, now 5 words" and "3 mistakes, now 4 words") show it changing. Settings keeps its button under Text to type and the Step up row with Start, Top and Down after, and the welcome explains it.
  - `mistakes` values `clear`, `delete` and `move` are Right key clears, Backspace to delete and Move on. The engine never reads `mistakes` or `suddenDeath` itself. It asks `mistakeWay(L)` and `restartsOn(L)`, which give Write's warm-up its own way (see Write).
  - Speeds are always stored in wpm, and a letter's speed is `12000 / ms`. cpm is for display only (x5).
  - `language` is `"en"` or `"zh"` (the Language setting, and the EN and 中文 switch under the text), `followInput` is Follow your input method, `pinyin` is Show pinyin and `pinyinSize` is Pinyin size (`"small"`, `"medium"` or `"large"`).
  - In Write, a piece is one thing you're writing (`state.writes`), its `list` is the word list and its `asks` are its questions, a warm-up test is a lesson with `warm` set (its `mode` is `"words"`) that holds one or more of those questions, and the draft is the textarea you write the piece in. `Write.phase` is `"warm"` or `"draft"`. On the server the list is a field, as in semantic field (`/api/write/field`), and the page uses the word for the list as it shows under a piece (`renderField`, `Write.field`). `writeWords` is Words per warm-up test and `writeFollow` is Words follow your piece. `drillWords` is the length of a Practice these test, which Settings calls Practice these and the card on Analysis Words in each test.
  - `Account.step` `"confirm"` is a new account waiting for its emailed code and `"reset"` a new password waiting for one. On the server a sign up waiting for its code is `pending`.
  - `Cloud.kind` `"key"` is Cloud save with your own save Worker, and `"account"` an account. `Cloud.key` holds the save key or, for an account, the token, and the error `key` means a 401, which for an account is a session that ended.
  - The marker's `why` values `out`, `deleted`, `revoked` and `cleared` are Sign out (or Sign out everywhere), Delete account, signed out from another browser and Clear this browser. A text in `due` is still going up, and one in `held` didn't fit.

## Gotchas and invariants

- **Adding a setting** takes four things.
  - A DEFAULTS entry of the right JS type, because controls are cast by `typeof DEFAULTS[key]`.
  - For enums, a check in `hydrate`'s include lists or lookup tables.
  - Markup with `data-setting`. Seg buttons also need a `data-value` exactly equal to `String(value)`.
  - An `EFFECTS` entry, or changing the setting only saves it. The order of the effect checks in `setSetting` matters. Two effects are there for one setting each. `drill` gives a new Practice these test from the same plan when one is on, and `warm` a new warm-up test in Write when one is on, so `drillWords` and `writeWords` take hold at once without ending either, and do nothing anywhere else.
- **Adding a word pool** needs a `POOLS` entry and an `<option>` in `#set-pool`.
- **Adding a punctuation mark or symbol** needs a `MARKS` entry (ids are single characters, and `group: "symbols"` puts it under Symbols in Settings) and handling in `decorate`. Keep `decorate`'s step order, which is apostrophes, then pairs, then symbol joins, stand-in tokens and prefixes, then wraps, then end marks, with capitals last. Numbers use the id `1`. All of them only apply while the Punctuation and symbols switch is on. A mark with two sides also needs a `MARK_SIDES` entry, so the second row of keys shows both, one that's written with digits belongs in the list `marksOn` looks at before it shows the digits, and one that joins two words with no space belongs in `WORD_JOINS` (see Word counts). Give its chance in `decorate` an `up(mark)` factor, or a band in `bands` when it shares a roll with others, so it comes up more often while it's weak.
- **Word tiers.** `POOLS` slices `COMMON_WORDS` at 200 and 500, so the `WORD_TIERS` sizes (100, 100, 300, 500) and their order matter. A duplicated word shifts every later boundary. Keep the word list `<script>` before the main one.
- **Load order.**
  - Many functions use names that are declared later, such as `el`, `view`, `ZOOMS`, `POOLS`, `MARK_IDS` and `shiftX`. This only works because they first run inside `init()`, so don't add top-level calls into code that touches later names. Put new startup work in `init()`.
  - Syntax a browser can't parse stops the whole app, not just one feature. `splitPassages` and `titleFrom` already use regex lookbehind, and the code avoids `?.` and `??`.
- **The `el` registry** looks up most ids once, at load, for all sections. A renamed id becomes null and crashes somewhere else later. `#focusCap` must keep its inner span.
- **`[hidden] { display: none !important; }` is load-bearing.** Many elements set their own display and are hidden only through `hidden`.
- **`html, body { overflow-x: clip; }` is load-bearing too.** The board's build up glow (`.board::before`, `inset: -60px -80px`) reaches past the sides of a phone's screen. Without the clip the page scrolls sideways, and mobile browsers widen the layout viewport to fit it, so fixed things like the welcome dialog center on a page wider than the screen and run off its edge. Use `clip`, not `hidden`, which would make `body` a scroll container.
- **Themes.**
  - The dark palette is written twice (the `prefers-color-scheme` block and `:root[data-theme="dark"]`), and the two must stay identical. New variables also go in the light `:root`.
  - The System theme means there is no `data-theme` attribute.
  - The `<html data-theme="dark" data-font="ubuntu">` defaults must match DEFAULTS.
- **Zoom.** Any `data-zoom` value hides the keyboard deck, so Normal must remove the attribute.
  - `applyZoom` sets it only on the Practice view.
  - `setSetting` sets `zoomBack` before calling it.
  - In Text only, Esc leaves. On touch screens (`pointer: coarse`) the `#zenHint` button stays at the top as the way out, since there is no Esc. Elsewhere it is a fading hint that never takes clicks or focus (`tabindex="-1"`, `pointer-events: none`).
  - Entering Text only scrolls the cursor (or the Three lines window) into view, before the zoom animation starts, because the animation's scaling throws off measurements.
- **Text rendering.**
  - `charEls[i]` must line up with `lesson.text`. The caret and the trail span are not in it.
  - `paintChar` overwrites each char's whole className from `lesson.states` (0 waiting, 1 right, 2 right after a mistake, 3 wrong). Any new char class must be added inside `paintChar`.
  - The line-height 1.7 and `calc(1.7em * 3)` height drive `measureLines`. `.w` must stay inline-block with `white-space: pre`, and `.c` inline-block.
- **Layout reads return 0 while a view is hidden.** New layout-dependent code must rerun wherever `measureLines`, `drawHands`, `markNextKey` and `moveCaret` already do, which is showView, applyZoom, resize, `fonts.ready` and the lines and hands effects.
- **Keys on the board go down with yours.** `onBoardKey` listens for `keydown` and `keyup` on the document in the capture phase, ahead of `onKeyDown`, the welcome and every field, and only ever touches classes, so a key shows down with the next frame whatever the test is doing. Keep it free of anything that waits or measures.
  - `buildKeyboard` fills `codeEls`, each key on the board by the `code` of the key it stands for (`CODE_ROWS` for the letter rows, the names for Tab, Caps Lock, both Shifts, Backspace, Enter and Space, and each `BOTTOM_ROW` item's `codes`). Every key on the board needs at least one code, so a new key in `BOTTOM_ROW` needs `codes` too. A key is found by where it sits, not by what it types, so the board matches whichever layout it shows.
  - `.held` is a key that's down (`pressKey`), and `liftKey` takes it away on `keyup`, though never sooner than `APP.keyShow` after it went down, so a tap shorter than a frame still shows. `heldKeys` holds the codes that are down. Two codes can share a key (Enter and the numpad's, both Controls on a Mac, the up and down arrows), and it stays down until both are up.
  - Keyups go missing, so three things lift keys without one. Leaving the window or hiding the page lifts everything. Letting go of Command lifts every key but the modifiers, since macOS sends no `keyup` for a key let go while it's down. Any key event whose `shiftKey`, `ctrlKey`, `altKey` or `metaKey` is false lifts that modifier.
  - A Mac sends one event for each press of Caps Lock (a `keydown` going on, a `keyup` going off), and a keyboard that gives no `code` can't be trusted to send a matching `keyup`, so both get `tapKey`, down and straight back up. Fn only reacts where the browser reports it (code or key `Fn`). Many keyboards handle it themselves and tell the page nothing.
  - `.down` is `pressVisual`'s flash for a letter typed with no key event, as on a phone, and looks the same as `.held`. `pressVisual` skips it while `heldKeys` has anything, and still adds `.oops`, the red ring for a wrong key. The pressed look is quiet on purpose, a sink of `0.025` of a key's width and a 10% ink tint where it started at `0.04` and 22%, which the owner found too obvious, and a key with no fill of its own (Shift and the like) keeps a `--line` outline under the tint. It's meant to be noticed, not watched, so don't make it stronger. It moves the key with `transform`, never its size, so `placeCue` and `drawHands` measure a held key at most `0.025` of a key's width out of place.
- **Keyboard geometry.**
  - Every row is 15 units (`--U` is `100cqw / 15`), and `BOTTOM_ROW` adds up to 15 on both Mac and PC.
  - `LAYOUTS` rows have 13, 13, 11 and 10 keys, and `FINGER_PATTERNS` and `CODE_ROWS` must match.
  - Fingers 0 to 3 are the left hand, 4 to 7 the right hand and 8 the thumbs.
  - `drawHands` uses fixed SVG ids, so only one hands SVG can exist.
- **`keepPartial`** must run before `lesson` is replaced. `startLesson` and `clearLesson` do this, and `L.counted` stops double counting. `onResetClick` and `clearLocalInPlace` set `counted` themselves first, so a test half typed never puts its keys into a record that was just reset or into an account that was just signed in to. `showWriteSetup` and `openDraft` run it too. Text is generated before it runs, so generation sees the stats from before the partial test. It also hands the partial test's keystrokes to `unfinished`.
- **Keystroke capture.** `typeChar` works out `gap` before it touches `L.start` or `L.last`, notes a miss with `noteMiss` only when `errAt` goes from 0 to 1, and sets `L.gaps[i]` only for a first try that was right. Keep those three rules if you change how mistakes work, or the Analysis tab counts trail keys and Backspace retypes as new mistakes. None of it feeds speed, accuracy, letter stats or goals. `L.missed` goes up next to `noteMiss` and feeds Step up's step down and its dots, so the same rule keeps them from counting trail keys and retypes.
- **Stale settings refs.** A `const s = state.settings` captured before a `hydrate` goes stale.
- **`coolUntil`** is shared by `failAttempt` (whose `hold` is captured after `checkGoals`), `playCheer` (which adds `APP.cheerHold`) and `playBoom` (which adds `APP.boomHold`). `checkGoals` must stay between tests. While your piece is on the board in Write, any key and any change to the piece sends a celebration away without that wait (`dropCheer`, from `draftKey` and `onDraftChange`), which also brings `coolUntil` back to now. A plain `endCheer(true)` there left up to 3 s of it, and the first keys of a warm-up started right after were dropped with nothing on screen to say why.
- **Stepping down.** After each finished Step up test (English or Chinese), `finishLesson` adds a word for a perfect test, up to Top, keeps the length for fewer than `stepDown` mistakes and takes one word away for `stepDown` or more, never below Start. `stepDown` 0 turns that off, and it is clamped to `APP.stepDownMax` (5), which is as many dots as fit beside a two digit word count at 375px.
  - A mistake here is a place in the text that went wrong, counted once however many wrong keys it took. That's `lesson.missed`, which `typeChar` raises in the same step as `noteMiss`, when `errAt` goes from 0 to 1, so outside One mistake restarts it always equals the number of set `errAt` entries. (One mistake restarts sets `errAt` without raising it, which does no harm, since that try is thrown away and shows no dots.) Each of those places shows red in the text in all three Mistakes options (`.fixed` once typed right, `.bad` in Move on), as the trail before the cursor until it's fixed, or as `.cur.miss` at the cursor once Backspace has taken the trail away (`paintChar` adds it when `errAt` is set, the state is 0 and no trail shows, and `popTrail` repaints the cursor when the trail empties). A space has no letter to turn red, so a missed space at the cursor or a fixed one gets a `--miss-soft` block, and its dot shows in full with Show spaces as dots. The trail's extra wrong keys (and the blocked keys in Backspace to delete) are one place. Backspacing over a place in Move on doesn't take it back, as it still counts toward accuracy, so the dots never go down within a test. A Move on place you've backspaced over shows plain until you type it again, then red.
  - The counter is `#pips` after `#wordCount`, one `<i>` per allowed mistake that gets `.on` (filled in `--miss`) as places go wrong. `renderPips`, called from `updateLive` and `afterMerge`, builds and fills them and sets the `aria-label` and `title` ("2 of 3 mistakes"), with no visible words. It hides them unless the lesson's `mode` is `"step"` (so not in Words, Adaptive, My text or Practice these, whose mode is `"words"`), One mistake restarts is off, `stepDown` is above 0 and Start is below Top (at Top every test is the same length, as `artStep`'s `flat` also knows). At Start (`stepWords()` at or below `stepStart`) they get `.low`, which fades them, and the label adds ", already at the shortest". They have a fixed size and `flex: none`, so filling one moves nothing. Below 360px wide the board foot packs its pieces closer (a 10px gap and the dots 6px from the count), which leaves the progress line about 23px at 320px with three dots and only about 3px with five. The next test starts with all of them empty, since `lesson.missed` starts at 0.
  - A test that took a word away shows `noteStepDown`'s tag in the Perfect tag's place, `showFlourish(text, "down")`, grey (`.flourish.down`) with no ring, light, sound or hold. A test that reaches a goal shows the goal instead, as with a perfect test.
- **Celebrations come in three sizes, and they should stay different.** The harder a thing is, the bigger its moment, so clean typing outranks the daily typing goal (the owner asked for that, since five minutes without a mistake is more impressive than twenty or thirty of any typing).
  - A perfect test (no mistakes) gets `flourishPerfect`, a small `#flourish` tag above the text and a light along the letter row (`.sequence.shine`, ordered by each key's `--i`). It never holds keys. `perfectRun` counts perfect tests in a row and isn't saved. `checkGoals` returns the goals it celebrated, and a test that reaches a goal shows that instead.
  - The daily typing goal alone gets `playCheer`, the slow release overlay, about 7 s. `renderCharge` (called from `renderGoal`) builds up to it from `APP.chargeFrom` of the goal by setting `.charging`, `--charge` and `--breath` on the Typing today goal and the board. Only this goal has a build up.
  - The clean typing goal, alone or together with the daily one, gets `playBoom`, the boom, about 11.4 s and then a 1.5 s fade. `celebrate` picks it whenever the ids hold `clean`. - **Weak keys** (Extra practice for weak keys, `weakBoost`, on by default). Letters and marks are ranked apart, up to three letters (`weakLetters`) and up to two marks or digits (`weakMarks`), and both lists come in the same shape.
  - `weakLetters(p, s)` gives up to three letters as `{ch, weakness, why, speed, miss, usual, under, mark}`, with why `"slow"` or `"missed"`, whichever counts more. `speed` and `miss` are the key's own figures as typed, `usual` what it's held up against (the median letter speed, or for a mark the usual speed of marks like it), `under` true when a letter is slow against `targetWpm` rather than the median, and `mark` true for a mark or a digit, all for the titles.
  - `recentLetters` walks back from the newest English test with `k` (Chinese tests and old tests without `k` are skipped) until about `APP.weakChars` letters or `APP.weakTests` tests, and works out the window's pace (ms per key) and miss rate. A letter typed fewer than `APP.weakMin` times there (z, q, j) keeps walking back through older tests by itself until it has that many, and one with fewer in all doesn't rank. Each test's average for a letter counts as at most `APP.weakCap` times the pace, and each letter gets `APP.weakPrior` keys at the window's pace and miss rate mixed in, as `rankRates` does on the Analysis tab, so one long pause or one miss can't name a letter typed a few times. Its speed counts once half of `APP.weakMin` were timed. When fewer than six letters rank from the history, the overall letter stats in `p.keys` rank every letter (as the old ranking did). There's no fallback for a single letter, since the overall stats move a lot on one key.
  - `rankWeak` drops letters the word list can't practice. `poolLetters` (built once per pool) holds the letters at least `APP.weakWords` of its words hold, so Common words (200) never names j, q, x or z and Common words (500) never names j or z. The median is still taken over every letter.
  - `weakest` scores slowness against the median letter speed and against `targetWpm`, and mistakes by miss rate, the same formulas the old ranking used. A letter named anew needs a weakness of 0.2. The list it was given last time (`before`) is what keeps the names steady. Those letters stay named down to `APP.weakKeep`, rank with `APP.weakStick` of extra weakness, keep their places at the front of the list and keep their reason unless the other score beats it by 0.15. A reason kept that way only holds while its own score is above 0, so a key that's no slower than usual any more is never called slow, nor one that's rarely missed missed. New letters follow them weakest first, and ties go to the unclamped score and then the letter, so the same history gives the same list. `APP.weakKeep` does most of the steadying. A bigger head start (0.25) left a clearly weaker letter out in up to a tenth of tests, so it stays small. In simulated typists with three letters 1.25 to 1.3 times slower, the letters outlined change after 1 to 2% of Step up tests and 5 to 7% of Words tests (31 and 56% before these rules), and after 60 steady tests one 1.5 s pause on z named it in 1 to 6 of 60 trials and one miss of z, k or v in none (35 to 40 of 40 before). A row that brings its own `missed` score (the marks do) has it used in place of the letters' `(miss - 0.03) / 0.09`.
  - `weakCache` keeps the result until the history's length or newest `ts`, `targetWpm`, `wordPool` or the profile object changes, so it ranks once per finished test and never per keystroke. The letter row (`renderSequence`), the welcome and the next test (`wordsText`) all read the same cached list. `weakMarkCache` does the same for marks, and its key also holds the marks that are switched on. The list from before carries across a merge on the same layout (`weakCache.layout`), but not across a reload or a sign in that clears this browser (`clearLocalInPlace` drops both), so after one the order (weakest first again) or a near tie can come out differently once. Each draws a weak letter by its weakness, then a word of the pool that holds it, and every weak letter gets a word when there's room. The rest are drawn uniformly, as with the setting off, still avoiding the same word twice in a row, so they can hold weak letters too. `decorate` runs as before.   - Marks and digits. Letters keep their stats as you type (`applyKeyStats`, into `p.keys`). Marks and digits get the same figures worked out from the keys the newest tests kept, so nothing new is saved and tests typed before this count too. `markStats(p)` walks every test with `tx`, `mx` and `tm` that add up, and gives `keys` (each mark's stats, shaped like a letter's and folded with the same sums, `foldKey`) and `tests` (what each test saw of each mark, oldest first, shaped like a test's `k`). The digits show with Numbers and with any mark that's written with one (`%`, `$`, `+`, `=` or `^`).
  - `rankWeakMarks` ranks the marks in `marksOn` from `markStats(p).tests`, each on the newest `APP.weakMarkKeys` (60) times it was typed, however many tests back that goes, since a mark comes up once or twice a test and a window of tests left a rare one with too little to go by. It ranks from `APP.weakMin` (8) typed. A mark is only held up against marks like it, in three kinds, the digits, the marks typed with Shift (`UNSHIFT`) and the rest, so being a digit or needing Shift doesn't make a mark weak, and a mark is never held up against the target speed, which is a letter's. A kind's usual pace is the middle one of its marks' own paces once three are timed (so one slow mark doesn't drag along what it's held up against), and `APP.weakMarkPrior` (100) keys at that pace are mixed into each mark's speed, with the same `APP.weakCap`. `peer`, the middle speed of the kind's marks, is what `weakest` holds a mark up against, and with fewer than three of a kind timed it's 0 and only mistakes count there. Misses count against the rest of the kind (`usual`, at least 30 of its other keys and 1%), by the exact chance of that many or more (`missChance`, binomial), and only from two misses of the mark's own. `missed` is `-log10(chance) / 8.5`, so under 1 chance in 50 names a mark (0.2) and under 1 in 7 keeps it named (0.1). So a slip never names a mark, a typist who misses every mark alike has none that stands out, and no title can say a mark is missed 0% of the time. - **Word counts.** `wordEnds(text)` marks where the words of a test end and `countWords` adds them up. A space ends a word, and so does a run of `- / _ | \ + = ^ , ; :` that sits directly between two letters with no space (`WORD_JOINS`), so sea-green and and/or are two words each, as the owner counts them. A hyphen also joins a word and a number, so 24-hour is two words and 10-year-old three. - **Passwords and usernames.** `APP.passwordRounds`, the `keyprint:v1:` salt text and the NFKC step in `passwordProof` must never change, or every password stops working. Usernames and email addresses can't be renamed, because the salt includes them. Once `PEPPER` is set it must stay the same for good, since a changed one makes every `kp2` login answer `wrong` and a missing one makes them answer 503.
- **Never write account progress without the config identity checks.** Local saves, account configs and the account's main copy go through `saveLocal`, `saveCloudConfig` and `sendCloud`, which compare `cloudIdentity(cloudSeen)` with `cloudIdentity(readConfigNow())` first, and `adoptAccount` checks between its steps. The read that `pullCloud` asks for saves what it merged with `Store.save` behind the same check, and `keepFace` keeps a picture behind it too. Keep any new write behind those checks, or a stale tab writes one person's progress into another's account, or back over a sign out. `Account.switching` turns them off only in the tab that's doing the switch. Backup restore and daily copy restore still call `Store.save` directly, from the tab you're clicking in.
- **Never wipe on a plain `Signed out`.** Only `Revoked` clears a browser. An expired, idle or pushed out session, a password change elsewhere and a lost row all answer `Signed out`, and the progress here may be the only copy, so `sessionEnded` keeps it and stops. Every clear goes through `clearBrowser`, marker first.
- **The Vault never writes for an unknown session.** Its constructor writes nothing, `has()` answers `Signed out` while there are no tables, only `session-new` creates them (and the Worker calls it only after the Directory made or found the user), and every write checks the session again inside its transaction, so a sign out that lands meanwhile wins. A made up token must never create storage.
- **Internal routes stay unreachable from `/api/u`.** The Worker forwards only `https://vault/data/` plus `encodeURIComponent(name)` for a name that passed `nameKind`, with a fresh headers object holding only `X-Kp-Secret` and `X-Kp-Uid`. Never pass the incoming request or its headers on, and never build a Durable Object path from the URL.
- **Same origin only.** Never add an `Access-Control-*` header to `/api`, or other sites can use a visitor's account. Logs carry one route or reason word, never bodies, tokens, proofs, credentials or addresses. A passing problem answers 503, because the app reads 500 as a site that isn't set up.
- **The Worker reaches outside in three ways only.** Resend, for the account emails, and for Write's questions and word lists either Workers AI through the `AI` binding or, with a key, the Claude API. Each has a time limit (`AbortSignal.timeout`, since the file has no timers), and the two fetches each have their own secret. Nothing a visitor sends chooses the address or the model, and neither key ever reaches a response or a log. What goes to the model is the person's own prompt and text and, as a piece grows, the end of what they've written (unless they switched Words follow your piece off), inside tags, and what comes back is only ever used as questions to type and a list of words.
- **Durable Objects interleave** at every await that isn't storage. Count limits synchronously before the first await, and run each write in `transactionSync` with no await inside. The stateless Worker must never share a pending promise between requests, because a request that waits on another request's promise is cancelled as hung, and its promise then never settles. Share only settled values, as `googleKeys` does. Neither class uses timers, only the storage alarm, so no time is billed while idle. Keep `site-worker.js` free of imports, so Node can load a copy.
- **The token stays out of the page.** It lives only in `keyprint-cloud`, an account config's `url` stays empty, and the Cloud save inputs are filled only in key mode.
